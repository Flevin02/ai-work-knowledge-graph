# 1. 文档说明

## 1.1 文档目的

本文档定义“知脉”从“AI 工作知识图谱维护助手”重定位为“AI 知识工作智能体与工作流平台”后的目标产品、业务范围、总体架构、核心领域模型、交互流程、技术边界、验收标准和迁移策略。

本次调整不是在原有知识图谱页面上追加聊天框，也不是把现有文档抽取方法简单包装成 Agent。目标是建立一套完整、可解释、可恢复、可审计的知识工作自动化系统：

```text
业务目标或事件
  → 启动可恢复工作流
  → Agent 在受控范围内检索知识、查询图谱和调用工具
  → 生成有证据的分析与行动建议
  → 规则校验和人工审核
  → 执行获准操作并更新正式知识
  → 记录全过程并持续评估
```

## 1.2 与原 PRD 的关系

原 PRD `ai-work-knowledge-graph-maintainer-prd.md` 定义当前轻量产品的范围、架构和功能；本文档描述 Agent + Workflow 重构后的目标态。两份 PRD 都不记录实施状态、验证证据或下一任务，这些内容分别由 Git、`docs/tests/` 和 `docs/roadmap.md` 承担。

在本文档被正式确认前：

- 不把目标态能力描述成已经实现。
- 不因目标架构改变而直接废弃已经验证的导入、证据、图谱和审核能力。
- 不把本 PRD 中的迁移策略自动视为下一任务；只有 `docs/roadmap.md` 中的当前任务可以进入实施。

## 1.3 术语约定

| 术语 | 本项目中的定义 |
|---|---|
| 知识资产 | 原始文档、网页快照、结构化记录等可追溯事实来源 |
| 知识库 | 原始资料、元数据、版本、章节分片、索引、权限和审核事实的整体，不等同于向量库 |
| RAG | 运行时执行检索、上下文增强和生成或抽取的流程 |
| Knowledge Graph | 经过规范化和状态管理的实体、关系、属性及其证据索引 |
| GraphRAG | 组合文档检索、实体识别、图谱扩展和证据回查的混合检索过程 |
| Agent | 根据目标和当前上下文，在受限工具集合中动态选择下一步的模型驱动执行单元 |
| Workflow | 管理步骤、状态、分支、重试、超时、暂停、恢复和人工任务的可靠流程 |
| Tool | Agent 可以调用的受控能力；工具本身执行确定性参数校验、权限和领域操作 |
| Action Proposal | Agent 或规则生成、等待审批的结构化行动建议 |
| Human Task | 必须由人工判断、批准、修改或拒绝的工作流步骤 |
| 正式事实 | 已通过规则和人工边界确认、可以进入正式知识图谱的数据 |

# 2. 产品重定位

## 2.1 一句话定位

> 让 AI 基于企业资料和知识图谱完成有证据的分析，并通过可审计工作流把分析转化为可控行动。

## 2.2 产品形态变化

原产品以“导入资料并维护图谱”为主线：

```text
资料 → 抽取 → 审核 → 图谱展示
```

目标产品以“完成知识工作”为主线：

```text
目标或事件
  → 工作流
  → Agent 检索、推理和调用工具
  → 分析结果与行动建议
  → 人工或规则审批
  → 执行与知识更新
```

知识图谱从产品终点调整为知识基础设施之一；图谱页面仍然保留，但不再承担整个产品的首页和唯一价值表达。

## 2.3 核心产品价值

1. **知识可用**：不只保存资料，而是能够按业务目标检索、组合和解释知识。
2. **结论可证**：每个关键判断都能回到原始文档、章节、分片和图谱关系。
3. **流程可靠**：长耗时任务可以暂停、重试、恢复和审计，不依赖一次 HTTP 请求完成。
4. **行动可控**：Agent 只能在权限和工具边界内工作，高风险操作必须审批。
5. **知识可维护**：新的业务结果经过审核后反向更新知识库和图谱，形成持续闭环。
6. **能力可复用**：同一套检索、Agent、工具和工作流能力可以组合成不同业务模板。

## 2.4 产品能力分级

产品采用渐进式自治，不追求一次性实现完全自动化：

| 等级 | 名称 | 能力边界 |
|---|---|---|
| L1 | Ask | 只检索和回答，不能形成行动建议 |
| L2 | Analyze | 可以执行多步分析并形成结构化结论 |
| L3 | Copilot | 可以生成 Action Proposal 和发起工作流，等待人工审批 |
| L4 | Autopilot | 仅对明确授权的低风险操作自动执行，并保留完整审计 |

MVP 目标为 L3，不将 L4 作为默认能力。

# 3. 项目目标与学习目标

## 3.1 产品目标

1. 建立原始资料、RAG、知识图谱、Agent 和 Workflow 之间清晰的职责边界。
2. 完成一个可以稳定演示、可重复测试的端到端知识工作场景。
3. 让 Agent 的每次知识使用、工具调用和行动建议都可追踪。
4. 让工作流在模型超时、服务重启、人工暂停和重复事件下保持可恢复和幂等。
5. 让正式知识只来源于可验证证据和获准行动，不把模型输出直接当作事实。

## 3.2 AI 学习目标

项目需要真实覆盖并解释以下概念：

- 文档解析、语义分片和元数据建模。
- Embedding、向量相似度和模型版本兼容。
- 关键词、向量和图谱混合检索。
- Recall@K、Precision@K、证据有效率和无依据生成率。
- Tool Calling、结构化参数和工具结果反馈。
- Agent 计划、停止条件、上下文压缩和失败模式。
- 短期运行上下文、工作流状态和长期知识之间的区别。
- Prompt Injection、越权调用、数据泄露和高风险操作审批。
- Workflow 的幂等、重试、超时、补偿、信号和人工任务。

## 3.3 非目标

- 不以“用了 Agent 框架”或“Agent 数量多”作为完成标准。
- 不训练或微调基础模型。
- 不建设通用低代码工作流设计平台。
- 不建设可以执行任意代码、任意 SQL 或任意网络请求的通用 Agent。
- 不以聊天界面替代结构化任务、工作流和审核体验。

# 4. 目标用户与角色

## 4.1 业务用户

项目助理、产品经理、运营人员、行政人员和知识密集型岗位人员。他们通过自然语言目标、业务事件或固定模板发起任务，查看分析、证据和执行结果。

## 4.2 审核人员

对关键结论、知识变更和外部行动进行接受、修改或拒绝。审核人员不需要理解 Prompt、Embedding 或工具协议，但必须能够看到充分证据、影响范围和风险。

## 4.3 知识管理员

维护知识空间、资料版本、标签、实体规范、关系类型、失效来源和冲突事实，处理无法自动规范化的数据。

## 4.4 Agent / Workflow 管理员

管理 Agent 定义、可用工具、模型配置、工作流模板、风险等级、超时和重试参数；MVP 中可以由开发者承担，不实现完整企业级管理员系统。

## 4.5 开发与评估人员

维护 Fixture、标注集、Prompt、Schema、模型版本和评估结果，分析召回、工具调用、工作流稳定性和成本变化。

# 5. 业务场景

## 5.1 场景选择标准

适合进入本平台的业务应至少满足三项：

- 需要阅读或检索多份非结构化资料。
- 需要执行多个步骤而不是一次模型问答。
- 中间存在需要动态判断的路径。
- 结果需要证据、审批或审计。
- 可能调用已有业务能力或外部系统。
- 处理结果应反向更新知识或形成后续任务。

以下场景不应为了使用 Agent 而进入平台：

- 简单 CRUD。
- 单表条件查询。
- 完全确定的数学或规则计算。
- 一次关键词搜索即可解决的问题。
- 无法提供事实来源和验收标准的开放式闲聊。

## 5.2 MVP 主场景：项目需求变更影响分析与知识更新

### 背景

项目资料通常分散在 PRD、设计文档、会议纪要、任务清单和历史决策中。新增或修改一份需求后，人工难以及时识别受影响的功能、任务、负责人、风险和历史承诺。

### 用户目标

用户导入新版 PRD 或会议纪要，并要求系统：

1. 找出相对于历史资料的新增、修改和删除内容。
2. 找到相关的历史需求、设计、任务、人员和风险。
3. 解释影响路径和证据来源。
4. 生成候选知识变更和后续行动建议。
5. 在人工审核后更新正式知识图谱。
6. 输出结构化影响报告。

### 业务价值

- 展示 RAG 对历史资料的召回能力。
- 展示 Knowledge Graph 对依赖和影响路径的表达能力。
- 展示 Agent 的动态检索和工具选择能力。
- 展示 Workflow 的长流程、人工审批和失败恢复能力。
- 展示从分析到知识更新的闭环，而不是只做一次回答。

## 5.3 P1 场景：会议纪要行动闭环

系统读取会议纪要，结合已有项目、任务和责任人资料，识别新任务、状态变化、决策和冲突，生成任务候选并进入负责人确认流程。

## 5.4 P1 场景：制度或合同审查

系统检索制度、模板、历史案例和相关条款，识别缺失项、冲突项和风险项，生成逐条证据和整改建议，并进入专业人员审核流程。

## 5.5 P2 场景：故障诊断与运行手册执行

系统结合告警、日志摘要、拓扑关系、历史事故和运行手册形成诊断计划，调用只读诊断工具，给出处置建议；任何变更或回滚操作必须单独授权。

## 5.6 P2 场景：员工入职与知识交接

系统根据岗位、项目和人员关系检索相关资料，生成分阶段学习或交接计划，通过工作流跟踪阅读、答疑、任务和验收结果。

# 6. 产品范围

## 6.1 MVP 必须包含

### 知识层

- 知识空间和资料隔离。
- Markdown、TXT 和文本型 PDF 导入；DOCX 可作为阶段增强。
- 原始文件、解析文本、版本和内容指纹。
- 章节感知分片、Embedding 缓存和可重建向量索引。
- 元数据过滤、关键词检索、向量检索和图谱扩展。
- 实体、关系、证据、候选状态和正式状态。

### Agent 层

- 一个受限的知识工作 Agent。
- 可配置的系统提示、模型、最大步骤、超时和 Token 预算。
- 白名单工具注册和风险分级。
- 结构化 Tool Calling、工具调用记录和停止条件。
- 运行级短期上下文，不自动形成长期记忆。

### Workflow 层

- 至少一个固定业务工作流模板。
- 工作流运行、步骤运行、状态转换和事件时间线。
- 自动节点、Agent 节点、规则节点、条件节点和人工任务节点。
- 重试、超时、取消、暂停、恢复和幂等。
- 人工接受、修改、拒绝和补充信息。

### 产品体验

- 目标输入与模板选择。
- 工作流运行详情和实时进度。
- Agent 推理摘要、工具调用和引用证据展示。
- 待办审核中心。
- 知识检索、图谱和来源追溯。
- 影响分析报告和候选知识变更。

### 评估与治理

- 固定 Fixture 和人工标注问题集。
- RAG、Agent 和 Workflow 分层指标。
- 模型、Embedding、Prompt、Schema、工具和工作流版本记录。
- 审计日志、错误分类和敏感信息控制。

## 6.2 P1 范围

- 多个固定工作流模板。
- 文档版本差异和增量重建索引。
- 混合检索加权和可选 Reranker。
- Agent 运行上下文压缩和恢复。
- 外部只读连接器，例如 GitHub、工单或文档系统。
- 低风险批量审核和规则自动批准。
- 工作流模板参数配置和版本发布。

## 6.3 暂不纳入

- 多 Agent 自由协作或 Agent 群聊。
- 通用无代码 Agent/Workflow 设计器。
- Agent 自主创建新工具。
- Agent 直接执行任意 SQL、Shell 或网络请求。
- 无审批的正式知识写入和高风险外部操作。
- 企业级多租户、复杂 RBAC、计费和配额系统。
- 大规模分布式向量数据库和微服务集群。
- 生产级 OCR、复杂版面理解和多媒体知识处理。
- 自动训练、微调或持续修改基础模型参数。

# 7. 核心业务原则

## 7.1 事实源优先

原始资料和经确认的业务数据是事实源。向量、摘要、模型解释和图谱节点都是索引或派生表示，不得覆盖事实源。

## 7.2 证据约束结论

关键结论必须引用真实存在的文档、版本、章节、分片和原文。服务端必须验证引用归属、原文匹配和知识空间范围。

## 7.3 Workflow 拥有流程状态

Workflow 决定宏观步骤、状态、重试、超时、人工暂停和结束条件。Agent 不得以聊天历史替代工作流状态，也不得自行声明流程已完成。

## 7.4 Agent 只拥有局部决策

Agent 可以在某个步骤内决定调用哪个已授权工具、是否继续检索或是否请求补充信息，但不能修改工作流定义、提升自身权限或跳过强制节点。

## 7.5 工具执行确定性边界

工具负责参数校验、空间隔离、权限检查、幂等和领域规则。Agent 生成的参数不是可信输入，工具不得假设模型已经完成校验。

## 7.6 候选与正式事实分离

Agent、规则和抽取产生的数据首先进入候选区。只有满足自动批准规则或完成人工审批后，才能转为正式知识或执行外部动作。

## 7.7 运行状态与长期知识分离

- Agent Run Context：当前推理所需的短期上下文。
- Workflow State：流程状态、步骤结果和等待信号。
- Knowledge Base：可以跨运行复用的资料、事实和证据。
- Conversation History：仅用于交互连续性，不能自动升级为正式知识。

## 7.8 渐进式自治

默认自动执行只读检索和低风险分析；候选写入可自动生成但必须可审核；正式知识变更和外部副作用按风险等级审批。

# 8. 总体架构

## 8.1 逻辑架构

```text
用户请求 / 文档事件 / 定时任务 / 外部事件
                    │
                    ▼
┌────────────────────────────────────────────┐
│ 入口与任务路由                              │
│ 身份、知识空间、目标、模板、风险等级、幂等键 │
└─────────────────────┬──────────────────────┘
                      ▼
┌────────────────────────────────────────────┐
│ Workflow Control Plane                     │
│ 定义、运行、步骤、分支、重试、超时、信号、审批 │
└──────────────┬─────────────────────────────┘
               │ 调度 Service / Agent / Human 节点
               ▼
┌────────────────────────────────────────────┐
│ Agent Runtime                              │
│ 目标理解、局部计划、上下文、工具选择、停止条件 │
└──────────────┬─────────────────────────────┘
               │ Tool Calling
               ▼
┌────────────────────────────────────────────┐
│ Tool & Capability Layer                    │
│ 知识检索、图谱查询、版本比较、规则校验、建议写入 │
└──────────────┬─────────────────────────────┘
               ▼
┌────────────────────────────────────────────┐
│ Knowledge Plane                            │
│ 原始资料、章节、分片、向量、实体、关系、证据、版本 │
└──────────────┬─────────────────────────────┘
               ▼
┌────────────────────────────────────────────┐
│ Governance & Evaluation                    │
│ 权限、审批、审计、追踪、成本、质量、安全、评估 │
└────────────────────────────────────────────┘
```

## 8.2 宏观控制与局部决策

```text
Workflow：确定必须完成哪些阶段
  └─ Agent 节点：在单个阶段内决定如何完成目标
       └─ Tool：执行经过校验的确定性能力
```

例如需求影响分析工作流必须经过“检索、影响分析、证据校验、人工审核、应用变更”五个阶段；影响分析 Agent 可以动态决定先查图谱还是先查文档，但不能跳过证据校验和人工审核。

## 8.3 模块化单体边界

MVP 使用模块化单体，不立即拆分微服务。后端逻辑模块建议为：

```text
server
├─ knowledge       # 知识空间、资料、版本、章节和分片
├─ retrieval       # 关键词、向量、图谱和混合检索
├─ graph           # 实体、关系、证据、图查询和知识变更
├─ agent           # Agent 定义、运行、上下文和模型适配
├─ tool            # 工具注册、参数 Schema、权限和执行
├─ workflow        # 流程定义、运行、步骤、信号和人工任务
├─ proposal        # 行动建议、审批和应用
├─ governance      # 策略、风险等级、审计和安全
├─ evaluation      # 数据集、实验、指标和失败样例
└─ integration     # 模型、对象存储和外部系统适配
```

`common` 继续只保存真正跨业务复用的响应、异常、TraceId 和校验等技术能力，不放 Agent、Workflow 或知识业务模型。

## 8.4 同步与异步边界

- 普通查询、知识检索预览和运行状态读取使用同步 HTTP。
- 文档索引、Agent 运行和工作流执行使用异步运行模型。
- 前端通过 SSE 或等价的只读事件流接收进度，不依赖请求连接维持业务事务。
- 工作流状态必须持久化；SSE 断开不影响后台运行。
- 用户重新进入页面后按 `workflowRunId` 恢复状态和历史事件。

# 9. 知识与 RAG 架构

## 9.1 知识摄取链路

```text
原始资料
→ 保存原始文件和指纹
→ 确定性解析
→ 章节和结构识别
→ 语义分片
→ Embedding
→ 索引
→ 可选实体/关系候选抽取
→ 证据校验
```

每一阶段必须有独立状态和错误类型，不能统一记录为“AI 处理失败”。

## 9.2 分片要求

每个分片至少保存：

- `spaceId`
- `sourceDocumentId`
- `documentVersionId`
- `sectionId`
- `sectionPath`
- `chunkOrder`
- 原文内容
- 原文起止偏移或页码范围
- 内容指纹
- 分片策略版本

分片优先按标题、段落、列表、表格和页码等语义结构切分，再使用 Token 上限控制长度。固定长度只能作为超长结构的兜底，不得丢失章节和表头语义。

## 9.3 Embedding 与索引要求

- 文档和查询必须使用兼容的 Embedding 模型、版本和维度。
- 更换模型后创建新索引版本，不混用不同模型向量。
- 相同内容指纹、模型和分片策略下复用向量缓存。
- 向量记录必须能反查原始分片。
- 删除或失效资料时更新索引可见性，不直接删除审计记录。

## 9.4 在线检索链路

```text
查询目标
→ 查询分类和过滤条件
→ 关键词 / 向量 / 图谱召回
→ 候选合并和去重
→ 可选重排
→ 邻近上下文补全
→ 上下文预算控制
→ 返回带定位信息的 RetrievedEvidence
```

MVP 必须先按以下元数据过滤：

- 知识空间。
- 文档有效状态。
- 文档版本。
- 文档业务类型。
- 用户显式指定的项目、标签或时间范围。

## 9.5 混合检索策略

| 查询类型 | 优先策略 |
|---|---|
| 自然语言描述、相似语义 | 向量检索 |
| 编号、日期、专有名词 | 关键词或结构化查询 |
| 实体关系、依赖和影响路径 | 图谱查询 |
| 复杂业务分析 | 向量、关键词和图谱混合 |

MVP 不允许 Agent 自由拼接 SQL。Agent 只能调用参数化的检索工具，由检索服务决定查询实现。

## 9.6 GraphRAG 路径

```text
语义检索找到相关分片
→ 从分片识别或关联已有实体
→ 沿图谱展开有限跳数的邻居和依赖
→ 回到支撑这些节点和关系的原文证据
→ 组合文档上下文和图谱上下文
```

图谱展开必须限制：

- 最大跳数。
- 允许的关系类型。
- 最大节点和边数量。
- 知识空间和版本范围。
- 是否只使用已确认关系。

## 9.7 引用与证据验证

生成结果引用至少包含：

- 来源资料名称和版本。
- `sourceDocumentId`、`chunkId`。
- 章节路径或页码。
- 逐字引用。
- 检索方式和排序位置。

服务端必须验证：

1. 分片属于当前知识空间和资料版本。
2. 引用文本真实存在于分片。
3. 图谱关系的证据真实存在且未失效。
4. 模型未引用未提供的来源标识。

## 9.8 RAG 失败策略

- 召回为空：返回无法从当前知识得出，不允许模型凭常识补全业务事实。
- 召回冲突：保留冲突来源并进入分析或人工判断。
- 证据失效：结论标记为不可应用。
- 上下文超限：按证据覆盖率和业务优先级裁剪，并记录被省略范围。
- Embedding 不可用：允许显式降级为关键词/图谱检索，但必须展示降级状态。

# 10. Agent 架构

## 10.1 Agent 定位

MVP 只实现一个“知识工作 Agent”。它接收工作流分配的局部目标，在有限步骤内使用知识和工具完成结构化分析。

Agent 不是：

- 后台线程的别名。
- 文档抽取 Service 的新名称。
- 拥有全部数据库权限的万能执行器。
- 可以自行修改业务流程的自治系统。

## 10.2 Agent 运行模型

```text
接收局部目标和权限上下文
→ 读取已批准的工作流上下文
→ 判断是否需要工具
→ 生成结构化工具调用
→ 工具执行校验和领域操作
→ Agent 读取工具结果
→ 继续、请求补充信息或结束
→ 输出结构化 AgentResult
```

每次运行必须配置：

- Agent 定义版本。
- 模型供应商和模型名。
- Prompt 版本和输出 Schema 版本。
- 可用工具清单。
- 最大步骤数。
- 最大 Token 和成本预算。
- 单次调用超时和总运行超时。
- 知识空间、用户和风险上下文。

## 10.3 工具清单

MVP 工具建议为：

| 工具 | 风险等级 | 作用 |
|---|---|---|
| `searchKnowledge` | READ | 按条件执行混合检索 |
| `getSourceEvidence` | READ | 读取指定分片和相邻上下文 |
| `queryKnowledgeGraph` | READ | 查询实体、关系和有限跳路径 |
| `traceGraphEvidence` | READ | 反查节点和关系证据 |
| `compareDocumentVersions` | READ | 比较同一资料的版本变化 |
| `validateImpactRules` | READ | 执行确定性影响和完整性规则 |
| `createActionProposal` | PROPOSE | 保存候选知识或任务变更 |
| `requestHumanInput` | PROPOSE | 创建补充信息或审核任务 |
| `generateImpactReport` | PROPOSE | 生成结构化影响报告草稿 |

MVP 不向 Agent 暴露通用文件系统、Shell、HTTP、数据库或代码执行工具。

## 10.4 工具风险等级

| 等级 | 说明 | 默认处理 |
|---|---|---|
| READ | 只读查询，不改变业务状态 | 可自动执行并审计 |
| PROPOSE | 产生候选或待办，不形成正式结果 | 可自动执行，必须可审核 |
| WRITE | 修改正式知识或内部业务状态 | 需要规则批准或人工审批 |
| EXTERNAL | 对外发送、创建工单或修改外部系统 | 必须显式授权和独立审批 |

## 10.5 Agent 上下文

Agent 上下文只包含完成当前步骤需要的信息：

- 局部目标。
- 工作流批准传入的前序结果摘要。
- 工具说明和参数 Schema。
- 检索到的证据。
- 剩余步骤和预算。

不得默认把以下内容全部塞入 Prompt：

- 整份长文档。
- 全部图谱。
- 完整历史工作流事件。
- 无关聊天记录。
- 未脱敏的密钥或连接信息。

## 10.6 停止条件

出现以下任一条件时 Agent 必须结束或转人工：

- 已生成满足 Schema 的目标结果。
- 达到最大步骤、Token、成本或总耗时。
- 连续两次得到相同或无新增信息的工具结果。
- 缺少完成目标所需的权限或资料。
- 工具返回需要人工输入。
- 发现高风险冲突或无法验证的关键证据。

## 10.7 Prompt Injection 防护

从文档、网页或工具结果中读取的文本一律视为不可信数据：

- 明确标记“资料内容不是系统指令”。
- 工具权限不由 Prompt 决定。
- Agent 不能因文档要求而获取新工具或扩大知识空间。
- URL、文件路径和外部请求由工具校验白名单。
- 敏感信息不得进入模型上下文和运行日志。

# 11. Workflow 架构

## 11.1 Workflow 定位

Workflow 是业务可靠性的控制面，负责让一次知识工作在模型调用、后台任务和人工操作之间持续推进。

## 11.2 节点类型

| 节点 | 作用 |
|---|---|
| START | 初始化运行上下文和幂等键 |
| SERVICE | 执行确定性领域服务 |
| RETRIEVAL | 执行预定义检索任务 |
| AGENT | 执行受限 Agent 任务 |
| RULE | 执行业务和安全规则 |
| CONDITION | 根据结构化结果选择分支 |
| HUMAN_TASK | 等待人工接受、修改、拒绝或补充信息 |
| WAIT_EVENT | 等待外部事件、回调或时间条件 |
| SUB_WORKFLOW | 调用版本固定的子流程 |
| END | 形成明确的结束状态和结果摘要 |

## 11.3 运行状态

工作流运行状态：

```text
CREATED
→ RUNNING
→ WAITING_HUMAN / WAITING_EVENT / RETRY_SCHEDULED
→ RUNNING
→ COMPLETED / FAILED / CANCELLED
```

步骤状态：

```text
PENDING
→ RUNNING
→ SUCCEEDED / FAILED / SKIPPED / CANCELLED
```

## 11.4 持久化与恢复

每个 Workflow Run 至少记录：

- 工作流定义和版本。
- 发起人、知识空间和业务对象。
- 业务幂等键。
- 当前状态和当前步骤。
- 输入、输出摘要和安全过滤后的上下文。
- 步骤尝试次数、开始时间、结束时间和错误分类。
- 等待的人工任务或外部事件。
- Agent Run、Retrieval Run 和 Action Proposal 关联。

服务重启、浏览器关闭或 SSE 断开后，工作流必须能够从持久化状态继续，不重新执行已成功且不可重复的步骤。

## 11.5 重试原则

- 网络超时、限流和临时模型错误可以按策略重试。
- Schema 非法、权限不足和证据无效不能盲目重试。
- 每次尝试独立记录错误和耗时。
- 重试不得重复写入候选、正式知识或外部系统。
- 超过上限后进入人工处理或明确失败。

## 11.6 幂等原则

- 业务事件使用稳定 `idempotencyKey`。
- 步骤执行使用 `workflowRunId + stepKey + attempt` 标识。
- 候选知识变更使用业务对象、操作类型、目标和证据指纹去重。
- 审批动作只允许对当前有效版本生效。
- 应用正式变更时校验预期版本，避免覆盖新事实。

## 11.7 人工任务

人工任务至少显示：

- 当前工作流和业务目标。
- Agent 结论摘要。
- 受影响对象。
- 原文证据和图谱路径。
- 建议操作、风险等级和影响范围。
- 接受、修改、拒绝和请求补充信息操作。

人工修改后必须重新执行必要的 Schema、业务和证据校验，不能直接绕过校验写入。

## 11.8 Agent 与 Workflow 的边界

| 能力 | Workflow | Agent |
|---|---|---|
| 确定必须经历的阶段 | 是 | 否 |
| 持久化流程状态 | 是 | 否 |
| 重试、超时和恢复 | 是 | 仅报告结果 |
| 局部选择检索工具 | 否 | 是 |
| 判断信息是否足够 | 通过规则接收结果 | 是 |
| 跳过强制审核 | 否 | 否 |
| 提升权限 | 否 | 否 |
| 形成正式业务事实 | 仅通过批准后的领域服务 | 否 |

# 12. MVP 主工作流详细设计

## 12.1 工作流名称

`PROJECT_CHANGE_IMPACT_ANALYSIS`

## 12.2 触发方式

- 用户选择知识空间、目标项目和新版资料后主动发起。
- 文档新版本索引完成后，由用户确认是否发起。
- MVP 不因任意文档导入自动执行完整分析，避免不可控成本。

## 12.3 输入

- `spaceId`
- `projectNodeId`
- `sourceDocumentId`
- `documentVersionId`
- 分析范围和时间范围。
- 用户补充目标。
- 是否允许生成知识变更候选。

## 12.4 步骤

### 步骤 1：校验输入与权限

确认知识空间、项目、文档版本和用户权限；生成业务幂等键。失败时直接结束，不调用模型。

### 步骤 2：确认知识索引状态

确认文档已经完成解析、分片和索引。若未完成，则调用知识摄取子流程并等待结果。

### 步骤 3：版本差异分析

使用确定性规则比较同一资料版本，输出新增、修改、删除章节和无法稳定比较的部分。

### 步骤 4：历史知识检索

根据变更内容检索相关 PRD、设计、会议、任务、风险和决策，并沿已确认图谱关系展开有限范围。

### 步骤 5：Agent 影响分析

Agent 使用只读工具补充检索和图查询，输出：

- 变更摘要。
- 可能受影响实体。
- 影响路径。
- 风险和冲突。
- 缺失信息。
- 每条结论引用的证据。

### 步骤 6：规则和证据校验

服务端验证输出 Schema、实体归属、关系类型、引用原文、跨空间引用、重复候选和高风险字段。

### 步骤 7：生成 Action Proposal

将通过校验的建议保存为候选：

- 新增或修改实体。
- 新增、修改或失效关系。
- 新任务或任务状态变化。
- 新风险或风险等级变化。
- 请求补充资料。

### 步骤 8：人工审核

审核人逐项接受、修改、拒绝或要求补充信息。补充信息可以回到检索或 Agent 分析步骤，但必须限制最大循环次数。

### 步骤 9：应用获准变更

领域服务按版本和幂等规则更新正式知识图谱、证据和审核记录。失败时不把工作流标记为完成。

### 步骤 10：生成影响报告

输出最终报告，明确区分：

- 已确认变化。
- 已拒绝建议。
- 未解决冲突。
- 缺失信息。
- 执行结果。
- 来源和证据。

### 步骤 11：结束与评估

记录工作流耗时、模型调用、检索指标、工具成功率、审批结果和失败样例。

## 12.5 主流程图

```text
START
  ↓
输入与权限校验
  ↓
索引是否就绪？ ──否──→ 知识摄取子流程 ──┐
  │是                                      │
  └────────────────────────────────────────┘
  ↓
版本差异
  ↓
混合检索与图谱扩展
  ↓
Agent 影响分析
  ↓
Schema / 业务 / 证据校验
  ├─ 无有效结果 → 生成无依据报告 → END
  ├─ 需要补充信息 → HUMAN_TASK → 有限次数回到检索
  └─ 有有效建议
        ↓
    Action Proposal
        ↓
    HUMAN_TASK 审核
        ├─ 全部拒绝 → 报告 → END
        └─ 部分或全部接受
              ↓
          应用正式变更
              ↓
          生成影响报告
              ↓
             END
```

# 15. 数据持久化建议

## 15.1 目标数据库

如果确认进行架构重构，推荐目标态使用 PostgreSQL + pgvector：

- PostgreSQL 保存业务状态、图谱、工作流关联、审计和评估数据。
- pgvector 保存与业务元数据一致管理的向量索引。
- 原始文件通过 `ObjectStorage` 抽象保存，本地开发可用文件系统，后续可切换 MinIO/S3。
- 第一版不引入 Neo4j；关系表和递归查询能够满足有限跳图谱场景。

SQLite 可以保留为历史演示或最小离线 Profile，但不再作为并发 Agent 与长工作流目标环境。是否保留双数据库 Profile 需要单独评估测试成本，默认不同时维护两套行为不一致的数据实现。

# 16. API 与事件设计

## 16.1 REST 资源建议

```text
/v1/spaces
/v1/spaces/{spaceId}/documents
/v1/spaces/{spaceId}/document-versions
/v1/spaces/{spaceId}/knowledge-queries
/v1/spaces/{spaceId}/graph
/v1/spaces/{spaceId}/workflow-runs
/v1/spaces/{spaceId}/agent-runs
/v1/spaces/{spaceId}/human-tasks
/v1/spaces/{spaceId}/action-proposals
/v1/spaces/{spaceId}/evaluation-runs
```

API 使用资源语义。发起分析通过创建 `workflow-run` 表达，不使用 `/run-agent`、`/process` 或 `/execute-workflow` 等动作路径。

## 16.2 工作流事件流

前端事件至少包括：

- `workflow_started`
- `step_started`
- `retrieval_completed`
- `agent_started`
- `tool_call_started`
- `tool_call_completed`
- `human_task_created`
- `step_retry_scheduled`
- `step_failed`
- `workflow_completed`
- `workflow_failed`
- `workflow_cancelled`

事件只承载进度和已持久化状态引用；前端收到事件后仍可通过 REST 获取权威详情。

## 16.3 结构化契约

Agent、Tool、Workflow Step 和 Action Proposal 之间使用显式 DTO 和 Schema。自由文本只能作为说明字段，不得承载必须由程序判断的状态、权限、操作类型或实体标识。

# 17. 技术选型与决策建议

## 17.1 建议技术基线

| 层次 | 建议 | 说明 |
|---|---|---|
| 前端 | Next.js + React + TypeScript | 保留现有技术方向，增加任务、运行、审核和评估界面 |
| 后端 | Java 21 + Spring Boot 模块化单体 | 保留 Java 学习和领域分层，暂不拆微服务 |
| Agent/RAG | LangChain4j + 领域接口 | 使用模型、Embedding 和 Tool Calling；业务不依赖供应商对象 |
| 业务数据库 | PostgreSQL | 支持并发状态、事务、审计和扩展查询 |
| 向量检索 | pgvector | 与业务元数据一致管理，降低首版基础设施数量 |
| 图谱存储 | PostgreSQL 关系表 | 首版不因“知识图谱”强制引入 Neo4j |
| 文件存储 | ObjectStorage 抽象 | 本地文件系统起步，可替换 MinIO/S3 |
| 工作流 | 引擎抽象，优先评估 Temporal | 适合代码驱动的长流程、重试、信号和恢复 |
| 实时进度 | SSE | 只传运行事件，不持有业务事务 |
| 测试 | JUnit 5 + Testcontainers + 前端 E2E | 覆盖 PostgreSQL/pgvector、Fake 模型和恢复路径 |

## 17.2 工作流引擎选择

### 推荐：Temporal

适用于代码驱动、长时间运行、自动重试、服务重启恢复和信号驱动的流程。若采用 Temporal：

- Workflow 代码必须保持确定性。
- LLM、Embedding、数据库业务操作和外部调用必须放入 Activity。
- Human Task 通过应用业务表和 Workflow Signal 协作。
- Temporal 历史只承担执行状态，正式业务事实仍由业务数据库维护。

### 备选：Camunda

当 BPMN 可视化建模、业务人员配置流程和复杂人工任务成为核心需求时评估。MVP 没有这一明确需求，不建议同时引入 Temporal 和 Camunda。

### 备选：自研轻量状态机

适合只验证单一固定流程和学习状态转换，但必须自行承担恢复、并发、幂等、定时器和可观测性。若目标是深入学习工作流基础原理可以采用；若目标是尽快完成可靠业务闭环，优先选择成熟引擎。

## 17.3 Agent 框架边界

Agent Graph 或模型编排框架不等同于业务工作流引擎。LangChain4j 负责模型和工具交互，Workflow Engine 负责可靠执行；不让二者互相替代。

## 17.4 不建议首版引入

- Neo4j + Elasticsearch + 独立向量数据库的三套存储组合。
- Kafka、Redis 和微服务集群。
- 同时支持多个工作流引擎。
- Python Agent 服务与 Java 业务服务的双栈拆分。
- 需要 Agent 自主规划任意 DAG 的通用编排平台。

# 18. 安全、权限与治理

## 18.1 权限上下文

每次 Workflow Run、Agent Run 和 Tool Call 必须携带：

- 用户或系统主体。
- 知识空间。
- 允许的业务对象范围。
- 工具白名单。
- 风险等级。
- 可执行的最大自治等级。

工具不能只相信 Agent 传入的 `spaceId`，必须使用服务端权限上下文再次校验。

## 18.2 模型数据安全

- API Key 只从服务端安全配置注入。
- 不向模型发送无关文档和完整数据库记录。
- 真实企业资料是否允许发送到第三方模型必须由部署策略决定。
- 供应商、模型、区域和数据保留策略必须记录。
- 日志和评估样例默认使用虚构或脱敏数据。

## 18.3 高风险字段

负责人、金额、日期、合同状态、审批结论、外部通知和删除操作默认属于高风险变更，不允许 Agent 自动形成正式结果。

## 18.4 审计要求

必须能回答：

- 谁发起了什么目标？
- 使用了哪个工作流、Agent、模型、Prompt 和工具版本？
- 检索到了哪些资料和图谱关系？
- Agent 调用了哪些工具？
- 哪些建议被谁接受、修改或拒绝？
- 最终修改了哪些正式知识或外部对象？
- 失败、重试和恢复发生在什么位置？

# 19. 非功能要求

## 19.1 可靠性

- 工作流服务或应用重启后运行可恢复。
- 重复请求和重复事件不产生重复候选或正式变更。
- 模型超时不占用数据库事务。
- SSE 断开不影响后台运行。
- 外部副作用支持幂等键或补偿策略。

## 19.2 可观测性

每次运行统一关联：

- `traceId`
- `workflowRunId`
- `stepRunId`
- `agentRunId`
- `retrievalRunId`
- `toolCallId`
- `proposalId`

## 19.3 性能目标

MVP 目标不是高并发，而是稳定和可解释：

- 普通知识检索在本地标注集上 P95 不超过 2 秒，不含模型生成时间。
- 工作流状态查询 P95 不超过 500 毫秒。
- Agent 首个可见运行事件在受控环境下 5 秒内到达。
- 单次 Agent 默认最多 8 个工具步骤；具体值可通过实验调整。
- 单个知识空间的 MVP 验证规模为 1,000 份资料、20,000 个分片和 10,000 个图谱节点以内。

性能目标需要在确定硬件、模型和数据集后重新校准，不能用本地小样本直接声明生产能力。

## 19.4 成本控制

- 重复内容不重复生成 Embedding。
- 相同检索和模型输入是否缓存必须带模型、Prompt、权限和版本键。
- Agent 记录输入/输出 Token、请求次数、耗时和估算成本。
- 达到运行预算后转人工或失败，不允许无限循环。

## 19.5 可维护性

- Agent、Workflow、Tool 和模型供应商通过接口隔离。
- 工作流定义、Prompt、Schema 和工具契约均有版本。
- 运行记录引用不可变版本，不因配置更新改变历史含义。
- 领域 Service 不直接依赖模型或工作流引擎 SDK 类型。

# 20. 评估体系

## 20.1 RAG 指标

- 解析覆盖率。
- Recall@K。
- Precision@K。
- 证据有效率。
- 跨知识空间泄漏率。
- 无答案正确拒答率。
- 检索延迟。

## 20.2 Agent 指标

- 任务结构化完成率。
- 工具选择正确率。
- 工具调用成功率。
- 无效或重复工具调用率。
- 达到步骤上限的比例。
- 高风险越权尝试拦截率。
- 人工对 Agent 结论的接受、修改和拒绝比例。

## 20.3 Workflow 指标

- 运行成功率。
- 平均完成时间和等待人工时间。
- 步骤重试率。
- 恢复成功率。
- 重复事件幂等成功率。
- 人工任务超时率。
- 取消和失败原因分布。

## 20.4 知识质量指标

- 实体规范化准确率。
- 关系类型和方向准确率。
- 正式关系证据覆盖率。
- 冲突识别率。
- 失效来源发现率。

## 20.5 实验规则

每次实验一次只改变一个主要变量：

- 分片策略。
- Embedding 模型。
- `topK` 或阈值。
- Reranker。
- Prompt 版本。
- 聊天模型。
- Agent 最大步骤。
- 工具描述。

实验必须记录数据集、模型、参数、结果、失败样例和结论。

# 21. MVP 验收标准

## 21.1 知识摄取

- [ ] 原始资料、版本、章节和分片能够互相反查。
- [ ] 相同内容、模型和分片策略不会重复生成 Embedding。
- [ ] 文档失效后不会继续参与默认检索，但历史证据仍可审计。
- [ ] 解析、分片、Embedding 和索引失败具有不同错误状态。

## 21.2 RAG

- [ ] 固定标注集中 Recall@5 达到 80% 以上；若未达到，必须保留失败样例和原因。
- [ ] 引用证据的服务端反查有效率为 100%。
- [ ] 跨知识空间召回泄漏为 0。
- [ ] 无依据问题不会生成确定性业务结论。
- [ ] 查询记录能够回放检索参数和召回结果。

## 21.3 Agent

- [ ] Agent 只能调用当前运行授权的工具。
- [ ] 所有工具调用都有结构化参数、结果摘要和审计记录。
- [ ] 达到步骤、Token、成本或超时上限后能够安全结束。
- [ ] Agent 不能直接写入正式图谱或执行外部副作用。
- [ ] Prompt Injection Fixture 不会扩大工具和知识空间权限。

## 21.4 Workflow

- [ ] 主工作流覆盖自动、检索、Agent、规则、条件和人工任务节点。
- [ ] 应用重启后能够恢复未完成运行。
- [ ] 重复发起同一业务事件不会产生重复正式变更。
- [ ] 可重试错误和不可重试错误能够区分。
- [ ] 人工任务支持接受、修改、拒绝和补充信息。
- [ ] SSE 断开并重新打开后可以恢复完整运行状态。

## 21.5 主业务场景

- [ ] 导入新版 PRD 或会议纪要后可以发起影响分析。
- [ ] 系统能检索相关历史资料并展开图谱影响路径。
- [ ] Agent 输出受影响对象、风险、缺失信息和逐条证据。
- [ ] 系统生成可审核的 Action Proposal。
- [ ] 审核通过后正式图谱按幂等规则更新。
- [ ] 最终报告区分已确认、已拒绝、未解决和缺失信息。

## 21.6 验证层次

最终汇报必须分别说明：

1. 编译验证。
2. Fake 模型和 Fake Embedding 单元测试。
3. PostgreSQL/pgvector 和 Workflow 本地集成测试。
4. 浏览器端到端测试。
5. 真实模型受控实验。
6. 尚未覆盖的真实企业数据、外部系统和生产环境。

# 22. 演示脚本

1. 打开“项目需求变更影响分析”模板。
2. 选择虚构项目和知识空间。
3. 展示已有 PRD、设计、会议、任务和图谱关系。
4. 导入或选择一份新版 PRD。
5. 发起 Workflow Run，展示索引、检索、Agent 和规则节点进度。
6. 打开 Agent Run，查看使用过的工具、召回资料和证据，不展示隐藏思维链。

10. 打开最终影响报告，反查原文证据。
11. 展示一次失败或等待补充信息的恢复路径。
12. 以一句话收束：系统不是只回答问题，而是让知识工作在证据、审批和流程约束下可靠完成。

# 24. 重构与迁移策略

## 24.1 重构原则

- 可以调整核心架构，但不采用一次性删除全部现有能力的 Big Bang。
- 先完成一个新架构垂直切片，再迁移剩余入口和页面。
- 当前可运行版本必须保留 Git 回滚点和数据库备份方式。
- 迁移期间旧链路和新链路的事实状态不能静默混用。

## 24.2 阶段 0：架构决策与冻结基线

1. 确认本 PRD。
2. 确认主业务场景。
3. 确认 PostgreSQL/pgvector。
4. 确认 Temporal、Camunda 或轻量状态机。
5. 冻结当前可运行版本和测试证据。
6. 记录数据库、上传资料和 Git 回滚方式。

## 24.3 阶段 1：Knowledge Plane

1. 建立文档版本、章节、分片和 Embedding 模型。
2. 建立 PostgreSQL/pgvector 环境和迁移脚本。
3. 完成混合检索和 Retrieval Run。
4. 建立标注集并验证 Recall@K 和证据反查。
5. 暂不引入 Agent，先证明知识底座可靠。

## 24.4 阶段 2：Workflow Control Plane

1. 建立工作流定义、运行、步骤和事件模型。
2. 完成 Service、Retrieval、Rule 和 Human Task 节点。
3. 验证重试、恢复、取消、幂等和人工信号。
4. 使用 Fake Agent 跑通固定主工作流。

## 24.5 阶段 3：Agent Runtime 与 Tool Registry

1. 建立 Agent Definition、Run、Step 和 Tool Call。
2. 接入只读检索和图谱工具。
3. 增加 Proposal 工具和工具风险等级。
4. 增加步骤、Token、成本和超时限制。
5. 使用 Fake Model 验证工具选择和越权拦截。

## 24.6 阶段 4：主业务闭环

1. 实现项目需求变更影响分析工作流。
2. 完成 Action Proposal 和审核中心。
3. 应用获准知识变更。
4. 生成影响报告。
5. 完成浏览器端到端和真实模型受控实验。

## 24.7 阶段 5：扩展场景与稳定性

1. 增加会议纪要行动闭环模板。
2. 对比两个场景的工具复用率。
3. 增加失败恢复、成本和安全观测。
4. 评估是否需要 Reranker、外部连接器或图数据库。

## 24.8 数据迁移

当前项目不存在生产数据迁移承诺。重构前应明确二选一：

- **开发数据重建**：保留原始 Fixture，重新导入并生成新索引；推荐用于当前学习项目。
- **历史数据迁移**：迁移知识空间、资料、图谱和证据，并为缺失版本/分片字段补充可追溯迁移记录。

不得把旧向量直接写入新索引，除非模型、版本、维度和分片内容完全一致并经过校验。

## 24.9 回滚策略

- 重构前建立可识别的 Git 基线或发布标签。
- 数据库迁移提供向前脚本和备份恢复说明。
- 新架构使用独立 Schema 或数据库时，旧数据库保持只读备份。
- 外部操作在重构阶段默认关闭。
- 若主工作流未通过验收，可回退到原有资料、抽取和图谱能力，不宣称新架构完成。

# 25. 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 为 Agent 而 Agent | 固定规则也交给模型判断 | 固定流程和规则保留在 Workflow/Service |
| Agent 与 Workflow 混淆 | 聊天历史成为流程状态 | Workflow 独立持久化并拥有状态 |
| RAG 质量不足 | Agent 基于错误召回继续推理 | 先建标注集和证据校验，再接 Agent |
| Prompt Injection | 文档诱导越权工具调用 | 不可信内容隔离、工具白名单和二次权限校验 |
| 无限循环和成本失控 | 重复检索、重复工具调用 | 最大步骤、预算、无新增信息停止条件 |
| 幂等失败 | 重试产生重复任务或知识 | 业务幂等键、版本检查和 Proposal 指纹 |
| 状态不一致 | Workflow 完成但业务写入失败 | 以业务事务结果决定步骤状态，支持补偿和重试 |
| 基础设施过重 | 大量时间花在部署组件 | 模块化单体、PostgreSQL/pgvector，延后其他中间件 |
| 图数据库过早 | 数据模型和查询复杂度上升 | 首版使用关系表，基于真实查询瓶颈再评估 |
| 真实资料泄露 | 文档进入第三方模型 | Fixture、脱敏、部署策略和模型调用审计 |
| 审核负担过高 | 所有结果都需要逐条确认 | 风险分级、批量低风险审核和规则自动批准 |
| 评估失真 | 只展示一次成功模型调用 | 固定数据集、失败样例和分层验证 |

# 26. 成功标准

项目重构成功不以页面数量或 Agent 数量判断，而以以下结果判断：

1. 一个业务目标能够通过可恢复工作流稳定完成。
2. Agent 在限定工具和预算内完成真实的动态检索与分析。
3. RAG 召回、图谱路径和最终结论都可以回到证据。
4. 人工能够理解并审核 Agent 提出的行动建议。
5. 审批通过后的知识变更具备幂等、版本和审计记录。
6. 服务重启、模型超时、检索为空和人工等待都有明确恢复路径。
7. 系统能用 Fake 模型重复测试，也能用真实模型执行受控实验。
8. 第二个业务模板能够复用主要知识、Agent、工具和 Workflow 能力，而不是复制一套代码。
