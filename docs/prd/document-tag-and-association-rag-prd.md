# 1. 文档说明

本文档只定义文档内容关联、可选标签增强、文档关系图、有据问答及受控 Agent 扩展的产品目标、业务规则、功能交互、AI/RAG 架构、数据与接口边界、验收标准和回滚方案。实施状态由 Git 追溯，验证结论写入 `docs/tests/`，下一任务只写入 `docs/roadmap.md`。

# 2. 背景与问题

## 2.1 当前问题

当前系统对单份文档按章节分片，并让模型从每个分片中抽取项目、人员、任务、风险、决策等实体及实体关系。该实现具备结构化输出和证据校验能力，但存在以下产品问题；这些实体结果保留用于兼容和实验，不再作为文档标签与文档关联主线的必选识别目标：

1. 用户导入资料后的首要需求是判断“这份文档和哪些文档有关”，当前结果却以大量实体和实体关系为主，信息密度过高且缺少阅读主线。
2. 当前模型每次只看到一份文档的一个分片，没有看到同一知识空间中的其他文档候选，因此不能可靠回答“应该关联哪份文档”。
3. 模型可以输出任意小写关系类型。即使 JSON、引用和证据格式合法，也不代表关系类型符合业务语义。
4. 实体、关系、证据和冲突按分片平铺，用户需要理解技术抽取结构，才能找到真正有用的信息。
5. 文档之间缺少稳定、可筛选、可人工维护的主题标签，无法在用户主动需要时缩小候选范围或解释关联。
6. 当前图谱混合项目、人员、任务、会议、风险、文档等多种节点，容易形成难以阅读的关系网络。

## 2.2 调整方向

产品主线调整为：

```text
导入文档
  -> 解析、分片和摘要
  -> 默认根据文档标题、摘要、正文和显式引用召回候选文档
  -> 可选使用已确认标签缩小或补充候选范围
  -> AI 判断文档与文档的关系并返回证据
  -> 人工采纳或拒绝关联建议
  -> 展示清晰的文档关系图和来源证据
```

文档是主视图中的一等节点。文档内容关联是默认关联条件，优先依据标题、摘要、正文、显式引用和后续可评估的语义检索判断；标签关联是可选增强条件，用于筛选、解释或补充候选，不因共同标签自动建立正式关系。项目、人员、任务等实体抽取保留为兼容能力或技术详情，不再作为来源资料页面的默认主内容，也不作为新文档关联闭环的前置步骤。独立“图谱类型”不再作为后续主线导航、筛选或新增 AI 识别范围。

# 3. RAG 后续计划与边界

## 3.1 哪些部分不一定需要 RAG

以下能力属于单文档理解或确定性处理，不要求先完成向量检索，也不要求标签已生成：

- 文档格式解析、章节识别和内容分片。
- 生成单份文档摘要。
- 从单份文档中生成候选标签。
- 用户手工新增、删除或修改标签。
- 根据明确文件名、文档编号或原文引用识别被引用文档。
- 根据文档标题、摘要、正文关键词和结构化字段筛选候选文档。
- 根据已确认的共同标签筛选或补充候选文档；该通道是可选的，不是默认关联条件。

这些能力可以通过规则、结构化模型调用和普通数据库查询实现。

## 3.2 哪些部分属于 RAG

“直接根据文档内容寻找相关文档”在候选较多或关键词不足时，需要在知识空间内先召回候选文档，再把候选文档的相关片段提供给模型判断，属于计划中的标准 RAG 链路：

```text
当前文档
  -> 生成检索查询或查询向量
  -> 在当前知识空间过滤和召回候选文档/分片
  -> 组装当前文档与候选文档的可定位上下文
  -> 模型判断是否关联、关系类型和证据
  -> 服务端验证文档标识、引用和原文片段
  -> 保存待审核关联建议
```

RAG 在本功能中的职责是“找到值得比较的候选文档和证据片段”，不是直接生成正式关系。向量相似度只能表示语义接近，不能证明两份文档存在业务关系。

## 3.3 第一版技术原则

1. 默认先实现文档内容关联，不等待标签或 Embedding 模型接通；最低链路使用显式引用、标题、摘要和关键词。
2. 标签提取作为可选增强能力独立实现；已确认标签可以筛选或补充候选，但不能单独确认关系。
3. RAG 和 Embedding 作为后续计划：先确认 OpenAI-compatible 端点支持的 Embedding 模型、维度和稳定性，再增加语义候选召回和上下文组装。
4. 向量召回加入后使用混合召回，不用向量检索替换确定性引用、标题、编号、正文关键词和可选标签查询。
5. 第一版继续使用 MySQL 保存事实、分片和可重建向量元数据，由 Java 在固定资料规模执行精确向量检索；没有规模证据前不引入外部向量数据库。
6. 当前默认使用可解释的固定 Pipeline；未来 Agent 只能作为外层编排器接入，不能替换领域规则、证据校验、审核状态机或知识空间隔离。

# 4. 产品目标

## 4.1 核心目标

1. 用户能快速理解一份文档的主题；在启用标签增强或已有确认标签时，看到少量、清晰、可编辑的标签。
2. 系统能在当前知识空间中找到与当前文档最相关的其他真实文档。
3. 每条文档关联建议都说明“关联哪份文档、为什么关联、由什么证据支持”。
4. 用户可以采纳、拒绝或后续重新评估关联建议。
5. 默认图谱只展示文档与文档的关系，避免多类型实体造成视觉噪声。
6. 文档、标签、关联、证据和运行记录都能追溯到具体知识空间、来源版本和模型配置。

## 4.2 学习目标

1. 理解结构化标签抽取与 RAG 候选召回的职责差异。
2. 通过固定资料集评估关键词、标签、向量和混合召回的 Recall@K 与 Precision@K。
3. 理解 Embedding 相似度、业务关系和模型置信度之间的区别。
4. 实践“召回候选 -> 模型判断 -> 服务端证据校验 -> 人工审核”的完整可信链路。
5. 记录 Prompt、Schema、Embedding 模型、检索参数和失败样例，形成可复现实验。

# 5. 非目标

第一版不包含：

- 自动把共同标签直接转成正式文档关系。
- 自动采纳高置信度关系。
- 标签本体、复杂层级分类、知识领域推理或自动标签聚类。
- 跨知识空间关联。
- 外部向量数据库、分布式索引或多实例同步。
- 将基于图谱的聊天问答、GraphRAG 或 Agent 编排作为第一版产品能力。
- 自动删除现有实体图谱数据。
- 生产级文档权限、多租户、敏感等级或外部分享。
- 扫描 PDF OCR、图片语义识别和复杂版面还原。

# 6. 用户与核心场景

## 6.1 目标用户

- 行政、人事和项目助理：整理活动方案、会议纪要、合同、通知和复盘。
- 运营和销售支持：查找同一项目或客户的相关材料。
- 研发和产品人员：查找需求、设计、会议和验收文档之间的联系。

用户不需要理解 Embedding、TopK、RAG 或向量数据库。技术参数只在运行详情中展示。

## 6.2 核心场景

### 场景 A：可选根据标签找到相关文档

用户打开《年会场地合同》，主动启用标签关联，选择已确认标签“年会、场地”。系统据此补充召回拥有这些标签的《年会活动方案》和《第一次筹备会议纪要》，再结合文档内容判断是否存在可审核的文档关系。未启用标签关联时，系统仍按默认内容关联流程工作。

### 场景 B：不依赖标签直接关联

《第二次筹备会议纪要》正文明确引用“第一次筹备会议纪要”并更新场地决定。即使标签尚未确认，系统也应先通过文件名、标题、显式引用和关键词找到旧文档，并建议 `updates` 或 `references` 关系；后续 RAG/Embedding 可作为语义召回增强。

### 场景 C：共同标签但不应关联

两份文档都带有“预算”标签，但分别属于不同项目。元数据过滤和内容判断应返回“不建立关系”，不能只凭标签相同生成建议。

### 场景 D：用户手工维护标签

AI 把“活动筹备”误识别为“活动策划”。用户可以修改或拒绝候选标签，也可以手工新增“年会”。手工标签直接成为已确认标签，并记录操作者和时间。

### 场景 E：来源发生变化

用户重新导入同一文档的新版本后，旧标签和旧关联不直接删除，但标记为需要重新评估。新运行基于新内容指纹生成候选，历史审核记录继续保留。

# 7. 核心概念

## 7.1 来源文档

来源文档是用户真实导入并持久化的 `source_documents` 记录。文档关系图中的文档节点必须直接来自有效来源文档，不允许模型自由创建不存在的“文档实体”。

## 7.2 标签

标签是对文档稳定主题或用途的简短描述，例如“年会”“会议纪要”“场地”“预算”。标签用于：

- 文档卡片展示和筛选。
- 缩小候选文档召回范围。
- 解释关联建议中的共同主题。
- 支持后续知识空间内的导航和健康检查。

标签不是事实关系，也不替代原文证据。

## 7.3 文档关联

文档关联的主体和客体都必须是当前知识空间内真实存在且有效的来源文档。关联有方向、类型、状态、生成方式、置信度、解释和证据。

## 7.4 关联建议

关联建议是尚未通过人工确认的文档关系。所有 AI 生成关系初始状态固定为 `suggested`。采纳后变为 `confirmed`，拒绝后变为 `rejected`，来源失效或内容变化后可变为 `stale`。

# 8. 标签业务规则

## 8.1 标签来源

标签来源分为：

- `ai`：模型生成的候选标签，必须经过人工确认。
- `user`：用户手工创建或编辑的标签，保存后直接确认。
- `rule`：由确定性规则产生，例如文档业务类型映射；第一版仅保留扩展位，不默认启用。

## 8.2 标签状态

- `suggested`：AI 建议，尚未审核。
- `confirmed`：已由用户确认或手工创建。
- `rejected`：已拒绝；在相同内容指纹和标签规则版本下不重复推荐。
- `stale`：文档内容发生变化，需要重新评估。

## 8.3 标签生成约束

1. 每份文档默认建议 3～8 个标签；原文信息不足时允许少于 3 个，禁止为了凑数量生成宽泛标签。
2. 标签应表达稳定主题、业务对象或文档用途，不提取日期、金额、临时状态和无意义高频词作为标签。
3. 标签展示名建议控制在 2～12 个中文字符或等价长度内。
4. 每个 AI 标签至少引用一条可以在当前文档分片中逐字反查的证据。
5. 同一文档内按 `normalizedKey` 去重；大小写、首尾空格和连续空格不应生成重复标签。
6. 第一版只做轻量规范化，不自动合并语义相近但文字不同的标签。
7. 标签别名和同义词只在有固定样本证明必要后引入，避免模型自动合并造成错误归类。

## 8.4 标签审核与编辑

1. 用户可以批量采纳或拒绝 AI 标签。
2. 用户可以新增手工标签。
3. 用户可以修改标签展示名；修改行为记录为“拒绝旧候选 + 新增用户标签”，不静默覆盖 AI 历史输出。
4. 用户删除已确认标签时采用解除文档关联，不物理删除全局标签记录。
5. 只有 `confirmed` 标签参与用户主动启用的标签筛选；`suggested` 标签不参与默认内容关联，只能在明确的实验或低权重可选通道中使用，并必须在关联解释中标识“尚未确认”。

# 9. 文档关联业务规则

## 9.1 关系类型白名单

第一版只允许以下关系类型：

| 关系类型 | 中文展示 | 方向 | 使用条件 |
| --- | --- | --- | --- |
| `related_to` | 内容相关 | 对称 | 两份文档围绕同一业务主题，且有可反查的内容依据，但不满足更具体类型 |
| `references` | 引用了 | 有向 | 主体文档明确提到客体文档名称、编号或唯一标识 |
| `supports` | 为其提供依据 | 有向 | 主体文档中的事实、合同、报价、记录或数据支撑客体文档 |
| `updates` | 更新了 | 有向 | 主体文档明确更新客体文档中的版本、状态、决定、时间或结论 |
| `conflicts_with` | 与其冲突 | 对称 | 两份文档对同一事实给出互不兼容的明确结论 |

未知关系类型、主体客体语义不匹配或方向无法判断的结果直接校验失败，不自动降级成 `related_to`。

## 9.2 关联生成方式

每条建议记录一个或多个生成依据：

- `explicit_reference`：文件名、标题、编号或原文明确引用。
- `tag_match`：拥有共同标签。
- `keyword_match`：标题、摘要或正文关键词命中。
- `semantic_match`：Embedding 语义召回。
- `hybrid`：多个检索通道共同命中。
- `user`：用户手工创建。

生成方式是解释和评估字段，不是关系类型。

## 9.3 关联成立条件

1. 主体和客体必须属于同一有效知识空间。
2. 不允许文档关联自身。
3. AI 建议必须引用服务端提供的真实候选文档标识，禁止模型返回自由文本文件名作为目标。
4. `references`、`supports`、`updates` 和 `conflicts_with` 必须至少包含一条直接证据。
5. `related_to` 至少包含两份文档各一条主题证据，或一条明确跨文档引用证据。
6. 共同标签只能用于召回和解释，不能单独把关系设为 `confirmed`。
7. 向量相似度和模型置信度只能用于排序，不自动决定审核结果。
8. 对称关系使用稳定的文档标识排序生成唯一键，防止 A-B 和 B-A 重复。
9. 有向关系按主体、关系类型、客体生成唯一键，同一版本下保持幂等。

## 9.4 审核规则

1. AI 关系默认 `suggested`。
2. 用户可以逐条或批量采纳、拒绝。
3. 拒绝时可填写原因；相同文档内容指纹、关系类型和算法版本下不重复推荐。
4. 用户手工创建关系直接为 `confirmed`，但必须选择白名单关系类型；证据允许后补，并明确标识来源为 `user`。
5. 来源文档软删除后，相关关系变为 `stale`，不物理删除历史记录。
6. 文档内容发生变化后，原关系继续可追溯，但在重新验证前标记“待重新评估”。

# 10. 用户流程

## 10.1 文档导入与基础内容分析

```text
用户导入文档
  -> 服务端保存原始文件和内容指纹
  -> 确定性解析章节、表格和正文
  -> 生成可定位分片
  -> 用户点击“AI 分析”或批量分析
  -> 模型生成全文摘要和文档内容候选关联
  -> 服务端校验关联证据和来源
  -> 文档卡片显示摘要和关联状态
```

## 10.2 可选标签增强模式

```text
用户主动启用标签关联
  -> 读取当前文档已确认标签
  -> 查找同一空间内共享标签的有效文档
  -> 排除自身、失效版本和已拒绝候选
  -> 读取候选文档摘要与相关分片
  -> 模型判断具体关系或返回无关系
  -> 服务端验证证据
  -> 保存待审核关联建议
```

## 10.3 默认文档内容关联模式

```text
从当前文档标题、摘要、正文和编号生成检索查询
  -> 显式引用召回
  -> 关键词/全文召回
  -> RAG 计划中可增加向量召回
  -> 合并候选文档并限制数量
  -> 检索每个候选的相关分片
  -> 模型逐候选判断关系或无关系
  -> 服务端验证并保存建议
```

## 10.4 关联审核

```text
用户查看关联建议
  -> 查看目标文档、关系类型、共同标签、解释和证据
  -> 打开双方原文定位
  -> 采纳或拒绝
  -> 已确认关系进入文档关系图
```

# 11. 信息架构与前端体验

## 11.1 来源资料卡片

默认展示；标签不存在时不阻塞内容关联：

- 文档格式和处理状态。
- 文档名称。
- 一段自然语言全文摘要。
- 如有已确认标签，最多展示 5 个；其余标签折叠为数量。
- 待审核标签数量和待审核关联数量。
- 已确认关联文档数量。
- “查看”“AI 分析”或“重新分析”等明确命令。

卡片不直接平铺候选实体、全部证据或技术运行参数。

## 11.2 文档详情弹窗

建议将现有三个 Tab 调整为：

1. `文档内容`：渲染预览和原文定位。
2. `AI 概览`：全文摘要、候选标签和标签审核。
3. `关联建议`：文档与文档的关系建议和审核。
4. `技术详情`：分片、模型、Prompt、Schema、Embedding、检索参数和原始结构化结果，默认折叠。

如果继续保留“渲染预览 / 原文预览”两个独立 Tab，则 AI 区域仍应拆成“标签”和“关联建议”，避免所有结果在一个长页面中平铺。

## 11.3 关联建议卡片

一张关联建议卡片只展示：

- 当前文档和目标文档名称。
- 中文关系类型。
- 一句话关联原因。
- 最多 3 个共同或相关标签。
- 1～2 条关键原文证据，可展开查看全部。
- “采纳”“拒绝”“查看目标文档”操作。

相似度、模型名、Prompt 版本和候选排名默认放入技术详情，不占用主阅读区域。

## 11.4 文档关系图

1. 默认节点只显示真实来源文档。
2. 默认边只显示 `confirmed` 文档关系；待审核关系通过筛选开关显示为虚线。
3. 支持按标签、文档类型、关系类型和状态筛选。
4. 点击文档节点进入 `/spaces/{spaceId}/documents/{documentId}` 文档详情页；详情页支持返回图谱并恢复知识空间、筛选条件、搜索词、选中节点和视口状态。
5. 文档详情页至少包含“文档内容、AI 概览、关联建议、问答上下文、技术详情”五个层次；原文、证据和引用可以定位到章节、分片或页码。
6. 默认聚焦当前文档及一跳邻居，不一次加载整个空间的全部节点；用户显式选择“查看全空间”后才加载全图。
7. 现有实体图谱保留为次级实验视图或功能开关，不与文档关系图混合渲染。

## 11.5 节点悬浮与关联高亮

1. 用户将鼠标悬浮或键盘聚焦到文档节点时，节点进入 `hovered` 状态；当前节点、直接相邻文档、相邻标签和连接边保持高对比度。
2. 与当前节点无直接关系的节点和边降低透明度，但不能消失、改变布局或导致节点位置跳动。
3. 同一悬浮状态下，关系边显示中文关系类型和审核状态；证据不足的候选边保持虚线和待审核色。
4. 移出节点或按 Escape 后恢复默认样式；点击节点进入详情页不依赖悬浮状态。
5. 键盘聚焦、触摸设备和无障碍模式必须有等价的“当前节点/一跳邻居”视觉反馈；不能只依赖颜色区分。
6. 高亮是展示行为，不改变关系状态、不触发模型调用、不写入数据库。

## 11.6 文档详情页与来源跳转

1. 文档详情页的主标识必须来自有效 `source_documents`，禁止根据模型返回的文件名创建虚假文档页。
2. 从图谱节点、关系建议卡片、标签筛选结果、问答引用和健康检查均可跳转到同一个文档详情 URL。
3. 页面显示文档名称、格式、业务类型、摘要、内容版本、标签、入向/出向关系、关系证据和最近分析运行。
4. “查看原文”只读取服务端解析内容；PDF 显示页码边界，Markdown/TXT 显示章节/行定位，不暴露本地存储路径。
5. 文档被软删除、版本变化或来源失效时，详情页保留历史证据和状态说明，不静默返回新版本内容冒充旧证据。

## 11.7 对话入口

1. 工作台和文档详情页提供“询问当前知识空间”入口；文档详情页默认将当前文档作为问题上下文，但用户可以移除该上下文。
2. 问答回复必须区分“回答正文”和“来源引用”，每条结论至少绑定一个服务端验证过的文档引用；无法找到证据时明确回答“当前资料不足”，不生成确定性结论。
3. 引用卡片显示文档名称、章节路径/页码、分片标识和原文摘录，点击引用跳转到文档详情页的对应定位。
4. 对话历史只保存当前知识空间范围内的会话元数据、问题、回答、引用和运行状态；不跨空间召回，不默认保存完整 API Key 或无关原文。
5. 问答首版只读，不允许通过聊天直接确认标签、采纳关系、删除文档或修改原始资料；需要变更时跳转到已有审核页面。

## 11.8 Agent 对话增强边界

1. 首版问答使用固定 Pipeline：问题解析 -> 当前空间过滤 -> 文档/分片召回 -> 上下文组装 -> 模型回答 -> 引用校验 -> 返回答案。
2. Agent 只在后续确有动态工具选择、长流程暂停/恢复、跨多步检索或需要人工介入时启用；不能因为页面出现聊天框就默认引入 Agent。
3. Agent 可以在受控工具中选择文档详情、候选召回、证据加载和引用校验，但不能开放任意 SQL、文件读写、HTTP、跨空间读取或直接写入确认关系。
4. Agent 回复必须复用 RAG 的引用契约；工具输出未经服务端证据校验不能进入最终答案。
5. Agent 运行单独记录 `runId`、步骤、工具、输入/输出摘要、耗时、重试、预算、状态和暂停原因；用户关闭页面或网络断开不能删除已保存运行记录。

## 11.9 空态与失败态

- 无标签：提示“尚未生成标签”，提供分析或手工添加入口。
- 无候选文档：说明当前空间内暂未找到相关资料，不生成空泛建议。
- 候选存在但无关系：说明已比较候选但没有足够证据，不展示模型内部否定结果列表。
- Embedding 不可用：默认继续使用显式引用、标题、摘要和关键词内容关联；如果用户已启用标签增强，再补充已确认标签通道，并在技术详情记录降级原因。
- AI 调用失败：保留已完成的解析、标签和召回结果，不把部分模型输出当作完整建议。
- 证据校验失败：建议不进入可审核列表，运行详情保留失败原因。

# 12. AI 输出契约

## 12.1 标签抽取输出

建议的结构化输出：

```json
{
  "summary": "文档全文摘要",
  "tags": [
    {
      "candidateId": "tag-1",
      "name": "年会",
      "confidence": 0.91,
      "evidenceIds": ["evidence-1"]
    }
  ],
  "evidences": [
    {
      "evidenceId": "evidence-1",
      "sourceDocumentId": "document-id",
      "chunkId": "chunk-id",
      "sectionPath": "活动背景",
      "quote": "2026 年公司年会筹备工作正式启动。"
    }
  ]
}
```

模型不得输出数据库标签标识、标签状态或审核结果。

## 12.2 文档关联判断输出

模型只能在服务端提供的候选文档列表中选择目标：

```json
{
  "evidences": [
    {
      "evidenceId": "source-evidence",
      "sourceDocumentId": "current-document-id",
      "chunkId": "current-chunk-id",
      "sectionPath": "会议结论",
      "quote": "第二次会议决定将湖畔酒店调整为首选场地。"
    },
    {
      "evidenceId": "target-evidence",
      "sourceDocumentId": "candidate-document-id",
      "chunkId": "candidate-chunk-id",
      "sectionPath": "暂定结论",
      "quote": "暂定星河会议中心为首选场地。"
    }
  ],
  "decisions": [
    {
      "candidateDocumentId": "candidate-document-id",
      "relationType": "updates",
      "direction": "current_to_candidate",
      "confidence": 0.86,
      "reason": "第二次会议纪要更新了此前暂定的场地结论。",
      "matchedTagIds": ["tag-id"],
      "evidenceIds": ["source-evidence", "target-evidence"]
    },
    {
      "candidateDocumentId": "another-document-id",
      "relationType": "none",
      "direction": "none",
      "confidence": 0.74,
      "reason": "只有宽泛的预算主题相同，缺少同一项目证据。",
      "matchedTagIds": [],
      "evidenceIds": []
    }
  ]
}
```

`direction` 固定为 `current_to_candidate`、`candidate_to_current`、`symmetric` 或 `none`；服务端根据当前文档、候选文档和方向计算最终主体/客体。`none` 只用于运行内部判断，不保存为文档关系，也不在默认用户界面展示。完整冻结语义和 JSON Schema 见 [`document-association-v1-contract.md`](../design/document-association-v1-contract.md) 与 [`document-association-output-schema-v1.json`](../design/document-association-output-schema-v1.json)。

## 12.3 服务端校验

服务端必须验证：

1. Schema 和 Bean Validation。
2. 候选文档标识属于本次服务端候选集合。
3. 主体、客体属于同一知识空间且不是同一文档。
4. 关系类型在白名单中，或为内部 `none`。
5. 证据文档、分片、章节和原文引用真实存在。
6. 引用没有跨文档错配，`quote` 可以逐字反查。
7. 对称关系顺序和唯一键规范化正确。
8. 同一运行不重复生成相同关系。
9. 标签标识属于主体或客体文档，且状态信息由服务端读取，不信任模型返回。

# 13. RAG 与混合检索设计

## 13.1 索引单元

- 文档级：文档名称、业务类型、全文摘要、已确认标签、内容指纹和版本。
- 分片级：`sourceDocumentId`、`sectionPath`、分片顺序、原文偏移、内容指纹和原文文本。
- 向量级：Embedding 模型、版本、维度、分片指纹、向量和生成时间。

查询向量与文档分片向量必须使用兼容的模型、维度和版本。模型变化后必须重建或隔离索引，禁止混用。

## 13.2 元数据过滤

所有召回通道执行前先过滤：

- 当前 `spaceId`。
- 文档状态为有效。
- 排除当前文档自身。
- 使用当前有效文档版本。
- 向量召回限定兼容 Embedding 模型和维度。
- 可选按文档业务类型或用户筛选条件过滤。

## 13.3 候选召回通道

1. **显式引用召回**：文件名、标题、文档编号和原文明确引用，优先级最高。
2. **关键词/全文召回（默认）**：标题、摘要、章节标题、编号、日期和关键短语。
3. **可选标签召回**：用户主动启用后使用已确认共同标签；未确认 AI 标签不能作为默认关联条件，只能作为低权重实验信号。
4. **向量召回（RAG 后续计划）**：使用当前文档摘要、标题和代表性分片检索语义相关分片；仅在独立实验达到门槛后启用。

第一版内容关联先使用显式引用、标题、摘要和关键词等可解释通道。未来加入 RAG/Embedding 后，再使用排名融合而不是直接相加不同量纲的分数；建议以 Reciprocal Rank Fusion 作为实验基线，并记录融合参数，是否保留该算法由评估结果决定。

## 13.4 可重复实验基线

首个实验默认参数：

- 显式引用候选：全部保留，上限 8。
- 关键词/全文候选：Top 8。
- 可选标签候选：Top 8；未启用标签关联时跳过。
- 向量候选：Top 8；RAG/Embedding 未启用时跳过。
- 融合后最多比较 12 份候选文档。
- 每份候选最多提供 3 个相关分片。
- 关联判断每批最多比较 4 份候选，避免上下文过长。
- 只保存通过业务和证据校验的非 `none` 建议。

以上参数是可复现实验起点，不代表已证明的最优值。每次调整必须固定资料集并只改变一个主要变量。

## 13.5 上下文组装

模型上下文必须包含：

- 当前文档标识、名称、类型、摘要、标签和相关原文分片。
- 候选文档标识、名称、类型、摘要、标签和相关原文分片。
- 每个分片的稳定 `chunkId`、`sectionPath` 和引用边界。
- 白名单关系定义和“证据不足时返回 none”的规则。

模型上下文不包含无关文档全文，不包含其他知识空间资料，也不把完整 API Key、存储路径或数据库连接信息发送给模型。

## 13.6 是否需要 Reranker

第一版不默认引入独立 Reranker。只有在标注资料表明 Recall@K 合格但 Precision@K 过低、模型比较成本明显过高时，再评估交叉编码器或模型重排。引入前必须记录它比现有混合召回多解决了什么问题。

## 13.7 有据问答 RAG 链路

文档关系关联和对话问答共享解析、分片、元数据过滤和证据校验基础设施，但输出目标不同：关联链路输出待审核关系，问答链路输出带引用的临时回答，不能把回答直接写成图谱事实。

```text
用户问题 + 可选当前文档
  -> 识别问题范围和空间边界
  -> 召回文档级候选和分片级证据
  -> 组装带文档名、章节路径、chunkId、页码/偏移的上下文
  -> 模型生成回答草稿和引用标识
  -> 服务端逐条校验引用与原文
  -> 返回回答、引用、置信提示和失败/无答案状态
```

问答契约至少包含：

- `conversationId`、`messageId`、`spaceId` 和问题范围。
- `answer`：面向用户的自然语言回答；不得把检索不到的内容写成确定事实。
- `citations[]`：`sourceDocumentId`、文档名、`chunkId`、章节路径、页码或偏移、原文摘录和定位 URL。
- `groundingStatus`：`grounded`、`partially_grounded`、`insufficient_evidence` 或 `failed`。
- `retrievalSnapshot`：召回通道、TopK、阈值、模型/Embedding 版本、候选数量和运行耗时；默认在技术详情折叠。

回答生成规则：

1. 引用必须来自本次服务端召回集合，模型不得自由填写文档 ID、文件名或页码。
2. 引用逐字反查失败时，该引用从最终回答中移除，并把运行标记为证据失败；不能把模型原文直接展示为可信来源。
3. 没有足够证据时返回明确无答案状态，可建议用户缩小问题、打开某份文档或补充资料。
4. 文档关系、标签和图谱事实可以作为回答上下文，但不能替代原始文档引用；图谱只提供索引和结构化线索。
5. 会话上下文按知识空间隔离，历史消息引用的文档版本失效时显示“来源已变化”，不能静默换成新版本。

首版问答不引入 Agent，不支持写操作，不支持多知识空间比较，不把对话内容自动沉淀为标签、关系或新文档。

# 14. Agent 扩展架构

## 14.1 为什么现在不直接引入 Agent

当前标签和文档关联流程是有限步骤、输入输出明确、需要强证据约束的固定 Pipeline：

```text
解析 -> 分片 -> 内容候选召回 -> 关联判断 -> 证据校验 -> 持久化 -> 人工审核
                 └-> 可选标签抽取/审核/候选补充
```

这条流程不需要 Agent 自主决定下一步。直接引入 Agent 会增加工具权限、状态恢复、循环调用、成本控制和测试难度，却不能自动提高标签或关联准确率。因此第一版不把 Agent 作为默认执行引擎。

## 14.2 未来适合引入 Agent 的触发条件

只有出现以下至少一种真实需求，才提交独立架构决策并评估 Agent 框架：

1. 一次分析需要根据中间结果动态选择多个工具或检索策略。
2. 长时间任务需要暂停，等待用户补充标签、选择候选文档或确认冲突后继续。
3. 运行需要跨多次请求恢复、重试、定时调度和人工介入。
4. 标签、关联、冲突和版本检查形成需要协调的多个专用角色或步骤。
5. 需要对复杂分析过程进行可回放、分支比较或失败节点重跑。

如果只是“调用一次模型生成标签”或“按固定步骤召回并判断文档关系”，继续使用普通 Service 和状态机，不为使用 Agent 而使用 Agent。

## 14.3 推荐的分层结构

未来可在现有领域服务外增加 Agent Orchestrator，但保持以下依赖方向：

```text
用户/API
  -> AnalysisApplicationService
      -> 可选 AgentOrchestrator（未来）
      -> 固定 Pipeline / Domain Services
          -> TaggingService
          -> CandidateRetrievalService
          -> AssociationDecisionService
          -> EvidenceValidationService
          -> ReviewService
          -> DocumentRelationRepository
```

推荐原则：

- Agent 只负责选择下一步、组织上下文和处理需要暂停的长流程。
- 领域 Service 负责业务规则、白名单、幂等、事务和状态变更。
- RAG Retriever 只负责召回和排序，不负责写入正式关系。
- `AiExtractionClient`、Embedding 接口和工具接口保持供应商无关。
- Controller 不直接依赖 Agent 框架对象。

## 14.4 Agent 工具契约

未来暴露给 Agent 的工具必须是有限、类型化、可审计的应用工具，而不是开放式数据库或 Shell：

| 工具 | 只读/写入 | 允许用途 | 必须校验 |
| --- | --- | --- | --- |
| `load_document_context` | 只读 | 读取当前空间指定文档的摘要、标签和分片 | `spaceId`、文档状态、字段脱敏 |
| `retrieve_document_candidates` | 只读 | 执行默认内容召回，并按用户选择补充标签或后续向量召回 | `spaceId`、TopK 上限、模型版本、关联通道 |
| `load_candidate_evidence` | 只读 | 读取候选文档相关分片和定位信息 | 候选集合归属、上下文预算 |
| `propose_tags` | 生成候选 | 生成候选标签，不写入确认状态 | Schema、标签数量、证据引用 |
| `propose_relations` | 生成候选 | 生成文档关系建议或 `none` | 候选文档集合、关系白名单、证据引用 |
| `validate_evidence` | 只读 | 逐字反查文档、分片和引用 | 当前空间、内容指纹、偏移 |
| `save_suggestion` | 写入候选 | 保存 `suggested` 标签或关系 | 幂等键、审核状态、事务边界 |
| `request_human_review` | 写入运行状态 | 暂停任务并生成待审核项 | 运行标识、待审核原因、可恢复状态 |

以下能力禁止作为 Agent 工具开放：任意 SQL、任意文件读写、任意 HTTP 请求、直接修改 `confirmed` 关系、删除来源文档、跨知识空间读取、直接写入向量索引。

## 14.5 Agent 状态和运行记录

如果未来引入 Agent，必须新增独立的 `agent_runs` 和 `agent_steps`（或等价领域模型），至少记录：

- `runId`、`spaceId`、主体文档、输入内容指纹和触发用户。
- Agent 框架、Agent 版本、工具策略版本和 Prompt/Schema 版本。
- 当前状态：`queued`、`running`、`waiting_review`、`paused`、`completed`、`failed` 或 `cancelled`。
- 每一步的工具名、结构化输入摘要、输出摘要、耗时、重试次数和错误类别。
- 下一步计划、最大步数、Token/费用预算和截止时间。
- 暂停原因、人工输入、恢复次数和最终结果引用。

不要只保存最终回答；必须能够根据步骤记录重放或定位失败节点。完整敏感原文、密钥和无限增长的思维链不进入运行日志。

## 14.6 Agent 的不可绕过边界

无论使用哪种 Agent 框架，以下约束都由服务端固定执行：

1. 所有工具调用先校验 `spaceId` 和主体文档权限。
2. Agent 只能选择服务端召回的候选文档，不能凭文件名创建新文档目标。
3. Agent 不能将 `suggested` 直接改为 `confirmed`。
4. Agent 不能跳过关系白名单、Schema、证据逐字反查和幂等校验。
5. Agent 不能把向量相似度或模型置信度当作审核结果。
6. 达到最大步数、预算或超时后必须停止并保存失败原因。
7. 工具重试必须幂等；重复恢复不得重复写入标签、关系或审核动作。
8. 用户关闭页面、网络断开或 Agent 失败不应删除已经保存的运行记录和候选结果。

## 14.7 框架替换边界

未来可以评估 LangGraph4j、Spring AI、LangChain4j AI Services 或其他 Agent/Workflow 框架，但替换范围应限制在 `AgentOrchestrator`、运行适配器和工具注册层。以下领域代码不应感知具体框架：

- 文档解析、章节和分片。
- 标签规范化与审核状态机。
- 候选文档召回和混合检索。
- 关系白名单、证据校验和幂等策略。
- 文档关系持久化、审核历史和健康检查。

框架评估至少比较：状态持久化、暂停恢复、工具权限、循环上限、可观测性、测试替身、故障重放、许可证、运行成本和与 Java 21/Spring Boot 的兼容性。

## 14.8 Agent 验收边界

Agent 只有在以下场景可重复验证后才能进入产品主线：

- 在固定资料集上完成标签和文档关联任务，结果不劣于固定 Pipeline。
- 中断后能从最后一个已提交步骤恢复，不重复写入。
- 人工审核暂停和恢复状态正确，拒绝结果不会被后续自动步骤覆盖。
- 工具越权、跨空间、未知关系类型和无效证据均被服务端拒绝。
- 达到预算、步数、超时和重试上限后可解释失败。
- 可以使用 Fake 模型和 Fake 工具执行自动测试，不依赖真实 API Key。

在这些条件满足前，Agent 只能作为实验性编排入口，不能替换当前固定 Pipeline。

# 15. 数据模型设计

## 15.1 设计原则

1. `source_documents` 是文档节点事实源，不复制为 AI 生成的 DOCUMENT 节点。
2. 标签、文档标签关系、文档关联和证据使用独立领域表，不强行复用现有实体 `graph_edges`。
3. 旧实体图谱表和历史抽取结果保留，不做破坏性迁移。
4. 所有表包含 `space_id`，并通过业务校验和外键防止跨空间引用。
5. AI 运行记录保存模型、Prompt、Schema、Embedding 和检索参数快照。

## 15.2 建议新增表

### `tags`

- `id`
- `space_id`
- `name`
- `normalized_key`
- `status`
- `created_at`
- `updated_at`

唯一约束：`space_id + normalized_key`。

### `document_tags`

保存文档和标签之间的候选或确认关系：

- `id`
- `space_id`
- `source_document_id`
- `tag_id`
- `source_type`：`ai`、`user` 或 `rule`
- `status`：`suggested`、`confirmed`、`rejected` 或 `stale`
- `confidence`
- `extraction_run_id`
- `content_hash`
- `prompt_version`
- `schema_version`
- `document_tag_key`
- `created_at`
- `updated_at`

唯一约束：`space_id + document_tag_key`。其中 `document_tag_key` 按第 17.1 节冻结签名计算，使相同内容和版本重复运行复用旧候选，Prompt 或 Schema 变化时保留新的候选历史；标签字典仍按 `space_id + normalized_key` 复用。

### `document_tag_evidences`

- `id`
- `space_id`

- `source_document_id`

- `reason`
- `operator_name`

唯一约束：`space_id + document_tag_id`。AI 标签只允许从 `suggested` 完成一次人工审核；重复或并发审核必须返回冲突，不能覆盖先到结果。

### `document_relations`

保存文档与文档的候选、确认、拒绝和失效关系：

- `id`
- `space_id`
- `source_document_id`
- `target_document_id`
- `relation_type`
- `status`：`suggested`、`confirmed`、`rejected` 或 `stale`
- `generation_mode`
- `confidence`
- `reason`
- `association_run_id`
- `source_content_hash`
- `target_content_hash`
- `created_at`
- `updated_at`

唯一约束按有向或对称关系的规范化签名生成。

### `document_relation_evidences`

保存关系两侧或跨文档的证据：

- `id`
- `space_id`
- `document_relation_id`
- `source_document_id`
- `chunk_id`
- `section_path`
- `quote`
- `start_offset`
- `end_offset`
- `evidence_role`：`source`、`target` 或 `cross_reference`
- `created_at`

### `document_relation_reviews`

保存不可变审核历史：

- `id`
- `space_id`
- `document_relation_id`
- `action`：`accept`、`reject` 或 `create`
- `reason`
- `operator_name`
- `created_at`

### `document_sections` 与 `document_chunks`

持久化确定性解析结果、章节路径、顺序、偏移和内容指纹。重复内容不重复解析；内容变化后生成新版本记录，不静默覆盖旧定位。

### `document_chunk_embeddings`

保存分片向量缓存：

- `chunk_id`
- `embedding_provider`
- `embedding_model`
- `embedding_version`
- `dimension`
- `content_hash`
- `vector_data`
- `created_at`

唯一约束覆盖 `chunk_id + embedding_model + embedding_version + content_hash`。

### `document_association_runs`

保存一次文档关联运行：

- 当前文档和内容指纹。
- 运行状态和失败阶段。
- 标签、关键词、向量候选数量。
- 最终比较候选及排名来源。
- Embedding 模型、Prompt、Schema 和检索参数。
- 模型请求次数、耗时、重试次数和建议数量。

### `conversations` 与 `conversation_messages`

保存知识空间内的只读问答会话和消息状态：

- `conversations`：`id`、`space_id`、标题、当前文档范围、状态、创建/更新时间。
- `conversation_messages`：`id`、`conversation_id`、角色、问题/回答正文、`grounding_status`、运行状态、错误类别、创建时间。

消息正文与运行记录分离，长回答可以通过运行标识恢复；不把未校验的模型中间输出标为最终回答。

### `message_citations`

保存回答引用和可定位来源：

- `id`、`space_id`、`message_id`、`source_document_id`、`document_content_hash`。
- `chunk_id`、`section_path`、页码或原文偏移、`quote`、引用顺序、校验状态。
- `retrieval_channel`、相似度/排名等技术字段可选保存，但不作为事实正确性的替代。

引用必须关联有效来源文档版本；来源变化后保留历史引用并标记 `stale`。

### `agent_runs` 与 `agent_steps`（后续可选）

只有进入 Agent 阶段才新增。运行至少保存 `space_id`、主体会话/文档、输入指纹、Agent/工具策略版本、状态、最大步数、预算、截止时间、暂停原因和最终消息引用；步骤保存工具名、结构化输入摘要、输出摘要、耗时、重试次数和错误类别。禁止保存完整 API Key、无关原文或任意 Shell/SQL 内容。

## 15.3 现有表兼容

- `ai_extraction_runs` 继续保留历史实体抽取结果；标签抽取是否扩展该表或使用独立运行类型，在详细设计阶段决定。
- `graph_nodes`、`graph_edges`、`evidences` 和 `review_actions` 不删除、不改写历史数据。
- 新的文档关系图查询 `source_documents + document_relations + document_relation_evidences`，不依赖模型创建 DOCUMENT 实体。

# 16. API 草案

API 继续使用 `/api/v1/spaces/{spaceId}` 前缀，Controller 不重复声明 `/api`。

## 16.1 标签资源

- `GET /documents/{documentId}/tags`：查询候选和已确认标签。
- `POST /documents/{documentId}/tags`：创建用户标签。
- `DELETE /documents/{documentId}/tags/{tagId}`：解除用户确认的标签。
- `POST /documents/{documentId}/tagging-runs`：创建 AI 标签分析运行。
- `GET /documents/{documentId}/tagging-runs/{runId}`：查询标签运行结果。
- `POST /documents/{documentId}/tag-review-batches`：批量采纳或拒绝候选标签。
- `GET /tags`：查询当前空间标签及文档计数，用于筛选器。

## 16.2 文档关联资源

- `POST /documents/{documentId}/association-runs`：创建关联分析运行。
- `GET /documents/{documentId}/association-runs/{runId}`：查询运行阶段和结果。
- `GET /documents/{documentId}/relations`：查询待审核和已确认文档关系。
- `POST /documents/{documentId}/relation-review-batches`：批量采纳或拒绝建议。
- `POST /documents/{documentId}/relations`：创建用户文档关系。
- `GET /document-graph`：查询当前空间的文档关系图。

## 16.3 有据问答资源

- `POST /conversations`：在当前知识空间创建只读问答会话。
- `GET /conversations/{conversationId}`：恢复会话元数据和消息摘要。
- `POST /conversations/{conversationId}/messages`：提交问题，返回 SSE 或可恢复的问答运行标识。
- `GET /conversations/{conversationId}/messages/{messageId}`：查询回答、引用和运行状态。
- `GET /documents/{documentId}/citations/{citationId}`：校验并打开文档引用定位。

## 16.4 Agent 运行资源（后续可选）

- `POST /agent-runs`：仅在满足 Agent 触发条件并显式选择 Agent 模式时创建运行。
- `GET /agent-runs/{runId}`：查询步骤、工具调用、暂停原因、预算和最终引用。
- `POST /agent-runs/{runId}/resume`：提交必要的人工输入后恢复暂停运行。

Agent 资源不得替代普通问答资源，也不得让 Controller 直接暴露具体 Agent 框架对象。

## 16.5 接口约束

- 服务端从路径和数据库读取主体文档，不接受客户端覆盖 `spaceId` 或主体文档标识。
- 审核接口只接收服务端建议标识和动作，不信任客户端重新提交的关系主体、客体、置信度或证据。
- 列表接口默认不返回完整原文和向量数据。
- 长耗时运行继续使用 SSE 或运行状态查询恢复，不把连接保持成功等同于模型结果正确。

# 17. 幂等、版本与增量更新

## 17.1 标签幂等键

```text
spaceId
+ sourceDocumentId
+ contentHash
+ normalizedTagKey
+ promptVersion
+ schemaVersion
```

相同输入和版本的重复运行复用或更新同一候选，不重复增加标签。

## 17.2 关联幂等键

```text
spaceId
+ normalizedSourceDocumentId
+ relationType
+ normalizedTargetDocumentId
+ sourceContentHash
+ targetContentHash
+ associationPolicyVersion
```

对称关系先规范化两端文档顺序。

## 17.3 文档变化

1. 内容指纹不变时，不重复生成分片、Embedding、标签和关联建议。
2. 当前文档内容变化时，其 AI 标签和相关关系标记为待重新评估。
3. 候选文档内容变化时，涉及该候选的关系同样需要重新评估。
4. Prompt、Schema、Embedding 或检索策略版本变化时创建新运行，不静默覆盖旧结果。
5. 已确认关系在新运行中不自动撤销；页面提示“来源已变化”，由用户重新确认。

# 18. 失败处理与可观测性

## 18.1 阶段化失败类型

必须区分：

- `parse_failed`
- `chunk_failed`
- `tag_extraction_failed`
- `embedding_failed`
- `retrieval_empty`
- `retrieval_failed`
- `association_model_failed`
- `structured_output_invalid`
- `evidence_invalid`
- `persistence_failed`
- `review_conflict`

不能统一显示成“AI 调用失败”。

## 18.2 降级策略

- 标签模型失败：保留原文、摘要回退和手工标签入口。
- Embedding 失败：使用默认显式引用、标题、摘要和关键词通道；仅在用户启用标签增强时补充标签通道。
- 某个候选判断失败：其他候选继续处理，失败候选记录原因。
- 全部召回为空：正常完成且返回“没有足够候选”，不记为系统异常。
- 证据无效：不保存为可审核建议。
- MySQL 写入失败：运行失败且不得只在前端保留不可恢复结果。

## 18.3 运行记录

记录：

- `runId`、`spaceId`、文档标识和内容指纹。
- 模型、Embedding 模型、Prompt、Schema 和策略版本。
- 各召回通道候选数、融合后候选数和最终比较数。
- TopK、阈值、上下文预算、重试和超时。
- 阶段耗时、Token、模型请求次数和失败阶段。
- 标签数、建议数、证据校验失败数和 `none` 数量。

日志不记录 API Key、完整敏感原文或完整向量。

# 19. 评估方案

## 19.1 固定评估资料

在 `fixture/` 中维护完全虚构或脱敏的版本化资料集，至少包含：

- 明确引用另一文档的会议纪要。
- 拥有共同标签且确实相关的文档。
- 拥有共同标签但属于不同项目的负样本。
- 更新旧结论的新版本文档。
- 明确冲突的两份文档。
- 内容相似但不应建立关系的模板文档。
- 没有任何相关文档的孤立资料。
- 长文档、表格、重复导入和版本变化。

每份资料标注预期标签、相关文档、关系类型和原文证据。

阶段 0 已在 `fixture/document-association-v1/` 冻结 `document-association-eval-v1`：包含 12 份自包含虚构 Markdown/TXT、7 条五种关系正例、5 组明确负例、7 个候选召回用例，以及表格、长文档、重复导入、版本变化和孤立资料场景。机器可读答案位于 `annotations.json`，实验规程见 [`document-association-evaluation-v1.md`](../tests/document-association-evaluation-v1.md)。静态验收已确认 JSON 合法、标识唯一、正负答案无冲突、五种关系均有正例，所有标签和关系证据均可在对应文件逐字反查。

阶段 2 另在同一目录冻结 `document-association-tag-threshold-eval-v2` 补充标注：它不修改 v1 正文或基础答案，只增加三条有逐字证据的人工 confirmed 标签，以及一个同项目双标签正例和一个跨项目双标签明确负例，用于隔离评估 `document-candidate-recall-v3` 数量阈值。

## 19.2 核心指标

- 标签 Precision、Recall 和 F1。
- 候选文档 Recall@K：正确目标是否进入前 K 个候选。
- 候选文档 Precision@K：前 K 个候选中有多少值得比较。
- 关系类型准确率。
- 关系方向准确率。
- 证据有效率：所有显示证据是否可以逐字反查。
- 无依据建议率：缺少证据时是否仍生成关系。
- 人工采纳率和拒绝原因分布。
- 重复建议率。
- Embedding 请求次数、聊天模型请求次数、Token、平均耗时和失败率。

## 19.3 首版质量门槛

在固定评估资料集上：

- 证据反查有效率必须为 100%。
- 跨知识空间建议数量必须为 0。
- 自关联和重复建议数量必须为 0。
- 候选召回 Recall@8 目标不低于 90%。
- 标签 Precision 目标不低于 85%。
- 非 `none` 关系建议 Precision 目标不低于 80%。

这些指标只证明固定资料集上的实验结果，不代表真实公司资料或生产质量。未达到门槛时优先修复解析、过滤、召回和证据问题，不直接通过扩大 Prompt 或更换大模型掩盖问题。

## 19.4 实验纪律

每次实验只改变一个主要变量：

- 标签 Prompt。
- 分片策略。
- Embedding 模型。
- TopK。
- 混合检索融合方法。
- 关联判断 Prompt。
- 聊天模型。

实验记录资料集版本、全部模型版本、Prompt/Schema 版本、检索参数、指标、失败样例、成本和结论。

# 20. 验收标准

## 20.1 标签验收

1. 用户可对一份文档生成候选标签，并看到每个标签的原文依据。
2. 用户可采纳、拒绝、编辑和手工新增标签。
3. 刷新页面后标签状态和审核历史可恢复。
4. 同一文档重复运行不生成重复标签。
5. 文档内容变化后旧标签被明确标记为需要重新评估。
6. 标签筛选严格限定当前知识空间。

## 20.2 文档关联验收

1. 系统默认通过文档标题、摘要、正文、显式引用和关键词找到候选文档，并可选通过共同标签补充候选。
2. Embedding 未启用、标签未生成或标签关联未开启时，仍可通过显式引用、标题、摘要和关键词完成最小关联链路。
3. 每条建议只指向真实文档，并显示关系类型、原因和证据。
4. 标签相同但缺少业务依据时不生成正式建议，或由模型返回内部 `none`。
5. 用户可采纳和拒绝建议，刷新后状态可恢复。
6. 拒绝建议在相同内容和策略版本下不重复出现。
7. 文档关系图默认只展示已确认文档关系。
8. 任何来源软删除或版本变化都会反映到关系状态。

## 20.3 RAG 验收

1. 分片、向量和查询使用兼容的 Embedding 模型、版本和维度。
2. 所有召回先执行 `spaceId` 和文档状态过滤。
3. 每次运行可恢复 TopK、候选来源、融合结果和最终上下文。
4. 正确文档召回和错误文档过滤使用固定标注样本验证。
5. 模型输出的证据全部由服务端逐字校验。
6. Fake Embedding 和 Fake AI 测试在没有真实 API Key 时可以重复执行。

## 20.4 前端验收

1. 文档卡片不再平铺候选实体和全部技术结果。
2. 标签和关联建议有清晰独立的信息层级。
3. 关联卡片在桌面和移动端不出现文字、按钮或证据重叠。
4. 点击文档节点、关系卡片、标签结果和问答引用都能进入同一文档详情页；返回图谱后筛选、选中节点和视口可恢复。
5. 悬浮或键盘聚焦节点时，一跳邻居、关联标签和连接边突出显示，非相关内容降权但不消失，移出后恢复。
6. 文档关系图与旧实体图谱不混合；标签关联开关关闭时不渲染标签节点和标签边。
7. 问答正文与来源引用分层显示，引用可以跳到章节/页码/偏移，来源失效、无答案和部分证据均有明确状态。
8. 空态、处理中、失败、降级、历史结果和来源变化都有明确状态。
9. 用户无需理解 RAG 或 Embedding 即可完成标签审核、关系审核和带出处问答。

# 21. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 标签数量膨胀和同义词重复 | 筛选混乱、召回噪声增加 | 限制单文档标签数量，先做轻量规范化，基于真实样本再引入别名 |
| 共同标签造成错误关联 | 用户失去信任 | 标签只用于召回；关系必须经过内容判断、证据校验和人工审核 |
| 向量相似但业务无关 | 大量误报 | 元数据过滤、混合召回、负样本评估和 `none` 输出 |
| Embedding 端点不可用或维度变化 | 索引无法使用 | 非向量降级、版本隔离、缓存和重建机制 |
| 候选过多导致模型成本高 | 延迟和费用上升 | 多通道先召回再融合，限制候选数和每候选分片数 |
| 文档变化导致旧证据失效 | 已确认关系不可追溯 | 保存内容指纹和偏移，标记 stale，不静默覆盖历史证据 |
| 模型被文档中的指令干扰 | 输出越权或结构失控 | Prompt 明确资料是数据，候选集合和关系白名单由服务端校验 |
| MySQL 并发事务冲突 | 批量分析失败 | 有界线程池、短事务、幂等键、运行状态恢复和写入失败重试边界 |
| 前端再次堆叠技术信息 | 可读性问题复发 | 默认只显示摘要、标签、文档建议和关键证据，技术信息折叠 |

# 22. 安全、隐私与隔离

1. API Key 只通过环境变量注入。
2. 所有检索和查询必须先限定 `spaceId`。
3. 不向模型发送本地存储路径、数据库连接串或无关文档全文。
4. 日志只记录标识、哈希、模型和错误上下文，不记录完整敏感原文。
5. 演示和自动测试只使用虚构或脱敏资料。
6. 不直接读取 `/Users/flevin/Documents/docs` 下的真实工作或个人资料。
7. 文档删除继续使用软删除，标签、关联和证据保留历史追溯。

# 23. 已确认产品与架构决策

以下设计决策是功能和架构边界，不表示对应代码已经实现：

1. **AI 标签必须审核**：AI 标签初始为 `suggested`；用户手工标签直接为 `confirmed`。
2. **文档关系图作为后续默认主图**：实体图谱保留为兼容/次级实验视图，不与文档关系图混合；切换默认主图前必须完成阶段 2 的固定资料验收。
3. **第一版关系类型固定为五种**：`related_to`、`references`、`supports`、`updates`、`conflicts_with`。
4. **默认内容关联、标签可选、RAG 后置**：先实现显式引用、标题、摘要和关键词内容关联；标签只作为用户可选的筛选/补充通道；RAG/Embedding 只有在固定样本证明非向量召回存在缺口后才进入实现。
5. **允许手工创建文档关系**：用户可以绕过 AI 直接创建白名单关系并补充说明。
6. **已确认关系不自动撤销**：来源变化后标记待重新评估，由用户确认是否修改。
7. **取消图谱类型主线**：不再在全局侧栏展示独立“图谱类型”，不把 `NodeType` 筛选作为文档关联主线验收项，也不把项目、部门、人员、任务等实体类型识别作为新增文档分析的必选目标。现有实体表、历史抽取结果、NodeType 字段和兼容查询不删除、不改写；如需保留旧筛选，只能作为实体图谱兼容视图的局部工具栏能力。

8. **文档详情和图谱交互**：文档关系图节点必须直接来自 `source_documents`；点击统一进入文档详情页，悬浮/键盘聚焦突出一跳邻居和关联标签，不能通过颜色以外的不可访问方式隐藏非相关节点。
9. **有据问答优先于 Agent**：先实现固定 RAG 问答、可点击引用和无答案状态；Agent 仅作为后续受控编排层，不能替代引用校验、审核状态机、知识空间隔离或固定 Pipeline。


# 24. 回滚方案

1. 新能力通过独立数据表、接口和前端功能开关接入。
2. 不删除或重写当前 `graph_nodes`、`graph_edges`、`evidences`、`review_actions` 和历史 `ai_extraction_runs`。
3. 如关联质量或性能不达标，关闭文档关联分析入口，保留标签和手工文档关系。
4. 如 Embedding 通道不稳定，关闭向量召回，退回显式引用、标签和关键词召回。
5. 如新文档关系图无法验收，恢复现有图谱入口；新表保留历史数据，不执行破坏性回滚。

# 25. 验收完成定义

本功能只有同时满足以下条件才能标记为“已完成”：

- 数据库、Service、API 和前端链路完成并通过自动测试。
- 标签和文档关系都有证据、状态和审核历史。
- 固定标注资料达到第 19.3 节质量门槛。
- Fake AI、Fake Embedding、本地 MySQL 和浏览器关键流程均完成验证。
- 文档关系图、详情页跳转、悬浮/键盘邻居高亮和问答引用定位均通过浏览器验收。
- 固定问题集的回答引用 100% 能回到有效文档版本和原文片段；无答案不会生成无依据结论。
- 若启用 Agent 编排，还必须达到第 14.8 节的恢复、人工暂停、工具越权、预算上限和 Fake 工具验证要求。
- 真实模型和真实 Embedding 的验证边界被单独记录，不能由 Fake 测试替代。
- 未验证的生产部署、真实公司资料和外部服务边界被明确说明。
