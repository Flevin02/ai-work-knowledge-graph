## 目标假设

当前按 2026 年 9 月提交作品倒排，具体提交日尚未确认。计划把 2026 年 9 月最后 7 天作为冻结和演示缓冲期；如果实际截止日更早，应优先冻结 P0/P1 功能，停止新增 P2 功能。

## 目标态验收顺序（2026-08-21 已确认）

```text
现有实体图谱兼容链路收口
  → 阶段 0 固定文档关联正负样本
  → 无 Embedding 的文档内容关联与人工审核
  → 可选标签及标签叠加图层
  → 文档关系图、详情页跳转和悬浮/键盘邻居高亮
  → Embedding/混合 RAG 评估
  → 固定 RAG 有据问答与引用定位
  → 满足动态编排条件后再评估受控 Agent
```

验收顺序是产品依赖关系，不代表上述目标态能力当前已有代码。每一步都必须保留正常、空、失败、恢复和回滚边界。

## 作品目标

形成一个边界清楚、主流程闭环、结果可解释、可以稳定现场演示的独立 Web 应用：

```text
导入办公资料
  → AI 提取实体、关系和证据
  → 人工审核关系
  → 交互式关系图谱
  → 健康检查和冲突提示
  → 导入新资料后增量更新
  → 导出 Markdown、JSON、图谱图片和办公摘要
```

专项方案评审通过后的目标主线为：

```text
导入办公资料
  → 生成自然摘要
  → 默认按文档内容召回候选文档
  → AI 判断文档关联并返回证据
  → 人工审核文档关系
  → 可选生成并确认标签，用于筛选或补充候选
  → 后续评估 RAG/Embedding 是否提升内容召回
  → 默认展示文档关系图
```

未来若出现动态工具选择、长流程暂停恢复或复杂可回放工作流，可在该主线外增加 Agent 编排层；Agent 只协调受控工具，不能直接确认关系、绕过证据校验或访问其他知识空间。没有这些实际需求时，继续使用固定 Pipeline。

## 功能优先级

### P0：必须完成，构成完整主线

- 独立 Next.js 项目和本地运行脚本。
- 知识空间创建、切换和删除。
- Markdown/TXT 文件导入。
- 内容指纹和重复导入识别。
- 实体提取：项目、部门、人员、任务、文档、会议、风险、决策。
- 关系提取和证据片段保存。
- 关系审核：接受、拒绝、修改。
- 关系图谱：缩放、拖拽、搜索、节点类型筛选、邻居展开。
- 节点详情：摘要、来源、证据、关系和更新时间。
- 图谱健康检查：孤立节点、待确认关系、失效来源、明显冲突。
- 虚构年会资料包和一键演示模式。

### P1：主线完整性增强，不扩张产品边界

- DOCX 和文本型 PDF 导入；扫描件 OCR、复杂版面还原和图片内容识别不在首版范围。
- 增量导入和版本差异预览。
- 时间线视图。
- 关系按确认状态、类型和时间筛选。
- Markdown 卡片和 JSON 图谱导出。
- 当前图谱视图 PNG 导出。
- 规则检查：任务缺负责人、任务缺截止时间、项目缺来源资料。
- 失败重试和本地演示快照。

### 暂不纳入首版

- 会议纪要自动转任务。
- 周报、交接材料、通知文案和海报生成。
- 多人协作、权限和多租户。
- 复杂的关系版本回溯。
- 可配置节点类型和关系类型。

这些功能不是做得越多越好；在核心链路稳定前，全部不进入实现范围。后续若有时间，只能在不改变主线数据模型的前提下评估。

## 开发纪律

- 先保证 P0 主线闭环，再补齐 P1 的完整性能力。
- “完成度”优先于“功能数量”：不为增加演示菜单而新增旁支功能。
- 每个功能必须同时具备正常态、空态、失败态和可恢复路径。
- AI 结果必须可追溯、可审核、可拒绝，不能只展示模型生成结果。
- 不把 EIS 源码、工作文档和个人知识库接入运行时。
- 所有 AI 关系都保留证据和审核状态。
- 所有演示资料都必须是虚构或脱敏内容。
- 每完成一个阶段，至少保留一个可运行版本和一条演示路径。
- 2026-09-14 之后原则上只做稳定性、易用性、视觉和演示修复，不再扩展产品边界。
