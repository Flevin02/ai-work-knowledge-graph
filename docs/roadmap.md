# 参赛开发路线图

更新时间：2026-08-19

## 目标假设

当前按 2026 年 9 月提交作品倒排，具体提交日尚未确认。计划把 2026 年 9 月最后 7 天作为冻结和演示缓冲期；如果实际截止日更早，应优先冻结 P0/P1 功能，停止新增 P2 功能。

## 作品目标

形成一个边界清楚、主流程闭环、结果可解释、可以稳定现场演示的独立 Web 应用：

```text
导入办公资料
  → AI 提取实体、关系和证据
  → 人工审核关系
  → 交互式关系图谱
  → 健康检查和冲突提示
  → 导入新资料后增量更新
  → 导出 Markdown、JSON、图谱图片和办公摘要
```

## 功能优先级

### P0：必须完成，构成完整主线

- 独立 Next.js 项目和本地运行脚本。
- 知识空间创建、切换和删除。
- Markdown/TXT 文件导入。
- 内容指纹和重复导入识别。
- 实体提取：项目、部门、人员、任务、文档、会议、风险、决策。
- 关系提取和证据片段保存。
- 关系审核：接受、拒绝、修改。
- 关系图谱：缩放、拖拽、搜索、节点类型筛选、邻居展开。
- 节点详情：摘要、来源、证据、关系和更新时间。
- 图谱健康检查：孤立节点、待确认关系、失效来源、明显冲突。
- 虚构年会资料包和一键演示模式。

### P1：主线完整性增强，不扩张产品边界

- DOCX 和文本型 PDF 导入；扫描件 OCR、复杂版面还原和图片内容识别不在首版范围。
- 增量导入和版本差异预览。
- 时间线视图。
- 关系按确认状态、类型和时间筛选。
- Markdown 卡片和 JSON 图谱导出。
- 当前图谱视图 PNG 导出。
- 规则检查：任务缺负责人、任务缺截止时间、项目缺来源资料。
- 失败重试和本地演示快照。

### 暂不纳入首版

- 会议纪要自动转任务。
- 周报、交接材料、通知文案和海报生成。
- 多人协作、权限和多租户。
- 复杂的关系版本回溯。
- 可配置节点类型和关系类型。

这些功能不是做得越多越好；在核心链路稳定前，全部不进入实现范围。后续若有时间，只能在不改变主线数据模型的前提下评估。

### 2026-08-24 ～ 2026-08-30：AI 抽取和关系审核

阶段前置进展（2026-08-19）：已完成 LangChain4j/OpenAI-compatible 适配、章节感知抽取、结构和证据校验、`ai_extraction_runs` 运行持久化、历史结果恢复、来源资料服务端分页、最近抽取状态恢复、当前页处理中状态轻量刷新、文本型 PDF 最小导入闭环、SQLite 有界连接池、SSE 流式抽取和既有来源资料隔离浏览器回归。真实 `gpt-5.4-mini` 已在 4010 服务返回一次同步完整结构化结果；约 37 秒延迟和一条关系类型语义误判说明当前仅验证了技术链路，尚未验证真实模型的流式兼容性。按最新任务顺序，下一项把 AI 输出并入来源资料查看弹窗，再继续关系白名单/规范化、候选入库和人工审核。

- 最高优先调整 `GET /api/v1/spaces/{spaceId}/documents`：使用服务端页码分页，并在每个列表项中返回最近一次 AI 提取状态，进入页面即可初始化“提取中、查看结果、重新提取、重试提取”等按钮状态。
- 来源资料列表默认每页 12 条，返回 `items`、页码、页大小、总数和总页数；文档与最近抽取摘要使用批量查询组装，禁止逐文档查询形成 N+1。第一版不做无限滚动，后续若切换为“加载更多”仍复用分页接口，不返回全量文档。
- 已完成文本型 PDF 导入：后端使用 PDFBox 保留逐页边界并继续按原始字节做 SHA-256 空间内去重；前端已同步文件选择、类型标签、统计和服务端文本预览。损坏、受密码保护、零页或无可提取文本的扫描 PDF 返回明确逐文件失败，首版未引入 OCR、DOCX 或复杂版面恢复。
- 在 Java 后端通过 LangChain4j 接入 OpenAI-compatible 模型，并使用 Jackson 和 Bean Validation 校验结构化输出。
- 通过 `AiExtractionClient` 抽象供应商和协议，首个实现允许配置 Base URL、模型名和 API Key，不把业务层绑定到具体模型产品。
- 已由 Spring Boot 自动配置有界 HikariCP，默认最大连接数 4、最小空闲 1、池获取超时 3 秒；每条 SQLite 连接启用 WAL、外键和 5 秒 `busy_timeout`。Java 21 根 Reactor 42 项测试通过，覆盖池耗尽、WAL 并发读、单写锁等待，以及池上限为 1 时 Fake 模型阻塞期间仍可导入和查看资料；尚未验证生产负载、多实例或真实模型并发。
- 实现结构化实体、关系、证据和冲突输出。
- 实现实体规范化和关系去重。
- 已将抽取接口实现为 `text/event-stream` 流式响应：前端实时消费运行、分片、真实模型增量、分片校验和终止事件；服务端只在完整响应通过 Schema、业务引用和证据校验并落库后发送完成事件。用户主界面显示中文进度、摘要和实体标签，模型原始 JSON 默认折叠为技术详情。

## 现场演示主线

1. 新建“2026 年公司年会”知识空间。
2. 导入第一批 7～8 份办公资料。
3. 展示 AI 识别出的实体、关系建议和证据。
4. 接受部分关系，拒绝一条错误关系。
5. 从“年会项目”节点展开部门、负责人、会议、任务和合同。
6. 打开一份来源资料，在“渲染预览 / 原文 / AI 输出”之间切换，观察抽取进度并查看证据片段。
7. 打开健康检查，展示孤立资料和缺少负责人提醒。
8. 导入第二次会议纪要。
9. 展示新增任务、状态变化和信息冲突。
10. 确认变更，生成项目摘要或周报。
11. 导出 Markdown、JSON 和图谱图片。

## 开发纪律

- 先保证 P0 主线闭环，再补齐 P1 的完整性能力。
- “完成度”优先于“功能数量”：不为增加演示菜单而新增旁支功能。
- 每个功能必须同时具备正常态、空态、失败态和可恢复路径。
- AI 结果必须可追溯、可审核、可拒绝，不能只展示模型生成结果。
- 不把 EIS 源码、工作文档和个人知识库接入运行时。
- 所有 AI 关系都保留证据和审核状态。
- 所有演示资料都必须是虚构或脱敏内容。
- 每完成一个阶段，至少保留一个可运行版本和一条演示路径。
- 2026-09-14 之后原则上只做稳定性、易用性、视觉和演示修复，不再扩展产品边界。
